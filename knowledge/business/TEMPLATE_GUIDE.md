## 📋 使用流程

### 场景 1: 我要添加一个新概念

**判断流程**：

```
这是一个基础概念吗？（如"活跃用户"、"帖子"）
    ↓ 是
使用 GLOSSARY_TEMPLATE.md
    ↓
添加到 glossary.md
```

**示例**：
- "沉默用户" → 使用术语模板
- "核心用户" → 使用术语模板
- "优质内容" → 使用术语模板

### 场景 2: 我要添加一个分析角度

**判断流程**：

```
这是一个分类或角度吗？（如"新老用户"、"内容类型"）
    ↓ 是
使用 DIMENSION_TEMPLATE.md
    ↓
添加到 dimensions/xxx_dimensions.md
```

**示例**：
- "用户等级（VIP/普通）" → 使用维度模板
- "内容类型（帖子/评论/问答）" → 使用维度模板
- "地域（省份/城市）" → 使用维度模板

### 场景 3: 我要添加一个业务指标

**判断流程**：

```
这是一个可量化的度量吗？（如"DAU"、"发帖数"）
    ↓ 是
    ↓
这个指标复杂吗？
    ↓ 简单（单表、简单聚合）
使用 METRIC_TEMPLATE.md
    ↓
添加到 metrics/xxx_metrics.md
    ↓
    ↓ 复杂（多表、复杂逻辑）
使用 METRIC_TEMPLATE.md + CALCULATION_TEMPLATE.md
    ↓
添加到 metrics/xxx_metrics.md + calculation_rules/xxx.md
```

**示例**：
- "日发帖数"（简单）→ 只用指标模板
- "人均发帖数"（中等）→ 只用指标模板
- "次日留存率"（复杂）→ 指标模板 + 计算规则模板

### 场景 4: 我要添加一个复杂的计算方法

**判断流程**：

```
这个计算很复杂吗？（多表、多步骤、易出错）
    ↓ 是
使用 CALCULATION_TEMPLATE.md
    ↓
添加到 calculation_rules/xxx.md
```

**示例**：
- "留存率计算" → 使用计算规则模板
- "漏斗转化率计算" → 使用计算规则模板
- "同期群分析计算" → 使用计算规则模板

## 🎓 模板核心概念详解

### 1. 什么是"口径"？⭐最重要

**定义**：
口径是统计数据时的**具体规则和边界**。

**为什么重要**：
```
同一个名称，不同口径，结果完全不同：

"DAU"（日活跃用户数）

口径1: 统计登录过的用户
  → 结果: 100万

口径2: 统计有任意行为的用户  
  → 结果: 150万

口径3: 统计有发帖行为的用户
  → 结果: 10万

差异巨大！必须明确口径！
```

**口径包含的要素**：

| 要素 | 说明 | 示例 |
|------|------|------|
| 统计对象 | 统计什么 | user_id、post_id |
| 聚合方式 | 如何聚合 | COUNT、SUM、AVG |
| 去重规则 | 如何去重 | 按 user_id 去重 |
| 时间粒度 | 时间单位 | 日、周、月 |
| 时间范围 | 时间边界 | 自然日 00:00-23:59 |
| 包含条件 | 什么算 | 行为类型 IN (...) |
| 排除条件 | 什么不算 | 排除测试账号 |
| 计算逻辑 | 计算步骤 | 先筛选，再去重，再计数 |

**如何写好口径**：

✅ **好的口径**（完整、明确）:
```markdown
**数据口径**:
- 统计对象: user_id
- 聚合方式: COUNT(DISTINCT)
- 去重规则: 按 user_id 去重，一个用户只计一次
- 时间粒度: 日
- 时间范围: 自然日 00:00:00 - 23:59:59，按行为发生时间
- 包含条件: 行为类型 IN (登录, 浏览, 发帖, 评论, 点赞, 交易)
- 排除条件: 排除 user_type IN ('test', 'internal', 'bot')
- 计算逻辑: 筛选日期 → 筛选行为类型 → 排除测试账号 → 去重计数
```

❌ **不好的口径**（模糊、不完整）:
```markdown
**数据口径**: 统计活跃用户数
```
**问题**: 
- 没有说明如何去重
- 没有说明时间范围
- 没有说明包含哪些行为
- 没有说明排除条件

### 2. 什么是"分类规则"？

**定义**：
分类规则定义了如何将数据划分到不同的类别中。

**核心要素**：

| 要素 | 说明 | 为什么重要 |
|------|------|-----------|
| **互斥性** | 一个数据只能属于一个类别 | 避免重复计数 |
| **穷尽性** | 所有数据都能分类 | 避免遗漏 |
| **边界明确** | 边界值的归属清晰 | 避免歧义 |
| **默认值** | 无法判断时的处理 | 保证完整性 |

**示例**：

✅ **好的分类规则**:
```markdown
**分类规则**:

| 类别 | 判断条件 | 说明 |
|------|---------|------|
| 新用户 | 注册天数 <= 30 | 注册30天内 |
| 老用户 | 注册天数 > 30 | 注册超过30天 |

**互斥性**: ✅ 是（一个用户只能是新或老）
**穷尽性**: ✅ 是（所有用户都能分类）
**边界**: 注册 = 30天算新用户
**默认**: register_date 为 NULL 时归为"未知"
```

❌ **不好的分类规则**:
```markdown
新用户: 注册时间比较短
老用户: 注册时间比较长
```
**问题**:
- "比较短"是多短？不明确
- 没有说明互斥性和穷尽性
- 边界不清晰

### 3. 什么是"引用关系"？

**定义**：
引用关系说明知识之间的依赖和关联。

**为什么重要**：
- 保证口径一致（引用统一的定义）
- 可追溯（知道知识来源）
- 便于维护（修改一处，影响清晰）

**如何建立引用**：

```markdown
**引用的术语**:
- [活跃用户](../glossary.md#活跃用户) - 定义了什么是"活跃"

**引用的维度**:
- [日](../dimensions/time_dimensions.md#日) - 定义了时间粒度

**引用的指标**:
- [新增用户数](user_metrics.md#新增用户数) - 作为分母
```

**引用的好处**：
- 点击链接可以跳转到定义
- 修改术语定义时，知道影响哪些指标
- AI 可以追溯知识来源

## 🔍 如何判断使用哪个模板？

### 决策树

```
我要添加的内容是什么？
    |
    ├─ 是一个基础概念（名词）
    |   → 使用 GLOSSARY_TEMPLATE
    |   → 示例: "活跃用户"、"帖子"、"交易"
    |
    ├─ 是一个分类/角度
    |   → 使用 DIMENSION_TEMPLATE
    |   → 示例: "新老用户"、"内容类型"、"地域"
    |
    ├─ 是一个可量化的度量
    |   |
    |   ├─ 计算简单（单表、简单聚合）
    |   |   → 使用 METRIC_TEMPLATE
    |   |   → 示例: "DAU"、"发帖数"
    |   |
    |   └─ 计算复杂（多表、复杂逻辑）
    |       → 使用 METRIC_TEMPLATE + CALCULATION_TEMPLATE
    |       → 示例: "次日留存率"、"转化率"
    |
    └─ 是一个复杂的计算方法
        → 使用 CALCULATION_TEMPLATE
        → 示例: "留存率计算"、"漏斗分析"
```

### 常见混淆

| 容易混淆 | 正确分类 | 判断依据 |
|---------|---------|---------|
| "日活" | 指标（DAU） | 可量化，有数值 |
| "活跃" | 术语（活跃用户） | 基础概念，无数值 |
| "新用户" | 术语 + 维度 | 既是概念，也是分类 |
| "新增用户数" | 指标 | 可量化，有数值 |
| "留存" | 术语（留存用户） | 基础概念 |
| "留存率" | 指标 | 可量化，有数值 |

**处理方法**：
- 如果既是术语又是维度 → 两个都创建
- 如果是指标 → 在指标定义中引用术语和维度

## 📝 填写顺序建议

### 推荐顺序

```
1. 先填写术语表
   ↓ 定义基础概念
   
2. 再填写维度定义
   ↓ 定义分析角度
   
3. 然后填写指标定义
   ↓ 组合术语和维度
   
4. 最后填写计算规则
   ↓ 提供复杂指标的实现
```

**为什么这个顺序？**
- 术语是基础，被所有人引用
- 维度引用术语
- 指标引用术语和维度
- 计算规则引用所有

### 实际操作

**第一步：列出所有术语**
```
活跃用户、新增用户、留存用户、流失用户、
帖子、评论、点赞、交易、订单...
```

**第二步：列出所有维度**
```
时间: 日、周、月
用户: 新老用户、用户等级、渠道
内容: 内容类型、内容标签
地域: 省份、城市
```

**第三步：列出所有指标**
```
用户指标: DAU、MAU、新增用户数、留存率...
内容指标: 发帖数、评论数、点赞数...
交易指标: 交易额、订单数、转化率...
```

**第四步：识别复杂指标**
```
需要计算规则的:
- 留存率（多表、复杂逻辑）
- 转化率（多步骤）
- 漏斗分析（多层级）
```

## 🎨 填写技巧

### 技巧 1: 口径要详尽

**原则**: 宁可啰嗦，不要模糊

❌ **不好**:
```markdown
统计活跃用户
```

✅ **好**:
```markdown
- 统计对象: user_id
- 去重规则: 按 user_id 去重
- 时间范围: 自然日 00:00-23:59
- 包含条件: 行为类型 IN (登录, 浏览, ...)
- 排除条件: 排除测试账号
```

### 技巧 2: 示例要具体

**原则**: 用具体例子说明抽象定义

❌ **不好**:
```markdown
活跃用户是有行为的用户
```

✅ **好**:
```markdown
示例1: 用户 A 在 2024-01-01 登录了 APP
  → ✅ 算活跃用户

示例2: 用户 B 只收到推送但未打开
  → ❌ 不算活跃用户
```

### 技巧 3: 关联要明确

**原则**: 明确标注引用关系

❌ **不好**:
```markdown
DAU 是日活跃用户数
```

✅ **好**:
```markdown
**引用的术语**: [活跃用户](../glossary.md#活跃用户)
**引用的维度**: [日](../dimensions/time_dimensions.md#日)
```

### 技巧 4: 错误要说后果

**原则**: 不仅说错误，还要说后果

❌ **不好**:
```markdown
不要使用 INNER JOIN
```

✅ **好**:
```markdown
❌ 错误: 使用 INNER JOIN
后果: 遗漏未留存用户，分母变小，留存率虚高（从30%变成100%）
✅ 正确: 使用 LEFT JOIN
```

## 💡 实际案例

### 案例 1: 添加"沉默用户"术语

**步骤**：

1. **判断**: 这是一个基础概念 → 使用术语模板

2. **填写**:
```markdown
## 沉默用户

**标准名称**: 沉默用户

**别名/黑话**: 
- 沉默
- 不活跃用户
- 流失预警用户

**定义**: 
在过去 N 天内没有任何行为记录的用户。

**数据口径**:
- 统计对象: user_id
- 时间范围: 过去 N 天（通常 N=7 或 30）
- 排除条件: 在过去 N 天内有任意行为的用户
- 包含条件: 注册时间 > N 天（排除新注册用户）

**相关术语**:
- [活跃用户](glossary.md#活跃用户) - 对立关系
- [流失用户](glossary.md#流失用户) - 相关概念
```

3. **添加到**: glossary.md

### 案例 2: 添加"用户等级"维度

**步骤**：

1. **判断**: 这是一个分类角度 → 使用维度模板

2. **填写**:
```markdown
## 用户等级

**维度名称**: 用户等级

**维度类型**: 用户维度

**分类规则**:

| 类别 | 判断条件 | 说明 |
|------|---------|------|
| VIP用户 | is_vip = 1 | 付费会员 |
| 普通用户 | is_vip = 0 | 非付费用户 |

**互斥性**: ✅ 是
**穷尽性**: ✅ 是
**默认值**: is_vip 为 NULL 时归为普通用户

**SQL 实现**:
```sql
SELECT 
    CASE 
        WHEN is_vip = 1 THEN 'VIP用户'
        ELSE '普通用户'
    END as user_level,
    COUNT(DISTINCT user_id) as user_count
FROM dwd_user_register
GROUP BY user_level;
```
```

3. **添加到**: dimensions/user_dimensions.md

### 案例 3: 添加"人均发帖数"指标

**步骤**：

1. **判断**: 
   - 这是一个可量化的度量 → 使用指标模板
   - 计算简单（两个指标相除）→ 不需要计算规则

2. **填写**:
```markdown
## 人均发帖数

**指标名称**: 人均发帖数

**指标类型**: 平均指标

**定义**: 
平均每个活跃用户发布的帖子数量。

**计算公式**: 
```
人均发帖数 = 总发帖数 / 活跃用户数
```

**引用的术语**:
- [活跃用户](../glossary.md#活跃用户)
- [帖子](../glossary.md#帖子)

**引用的指标**:
- [发帖数](content_metrics.md#发帖数) - 分子
- [DAU](user_metrics.md#DAU) - 分母

**数据口径**:
- 统计对象: post_id（分子）、user_id（分母）
- 聚合方式: SUM(发帖数) / COUNT(DISTINCT 活跃用户)
- 时间粒度: 日
- 计算逻辑: 总发帖数 / 活跃用户数

**SQL 逻辑**:
```sql
SELECT 
    date,
    SUM(post_count) as total_posts,
    COUNT(DISTINCT user_id) as active_users,
    ROUND(
        CAST(SUM(post_count) AS DOUBLE) / COUNT(DISTINCT user_id),
        2
    ) as avg_posts_per_user
FROM dws_user_daily
WHERE date = current_date
  AND is_active = 1
GROUP BY date;
```
```

3. **添加到**: metrics/content_metrics.md

### 案例 4: 添加"转化率"计算规则

**步骤**：

1. **判断**: 
   - 这是一个复杂指标 → 需要计算规则
   - 涉及多个步骤（漏斗） → 使用计算规则模板

2. **填写**:
```markdown
## 注册转化率计算规则

**适用指标**: 注册转化率

**计算公式**:
```
注册转化率 = 注册成功用户数 / 访问用户数 × 100%
```

**计算步骤**:

步骤1: 获取访问用户（分母）
步骤2: 获取注册成功用户（分子）
步骤3: 计算转化率

**SQL 模板**:
```sql
WITH visitors AS (
    SELECT DISTINCT user_id
    FROM dwd_user_behavior
    WHERE date = current_date
      AND behavior_type = 'visit'
),
registered AS (
    SELECT DISTINCT user_id
    FROM dwd_user_register
    WHERE register_date = current_date
      AND register_status = 'success'
)
SELECT 
    COUNT(DISTINCT r.user_id) as registered_count,
    COUNT(DISTINCT v.user_id) as visitor_count,
    ROUND(
        CAST(COUNT(DISTINCT r.user_id) AS DOUBLE) * 100.0 
        / COUNT(DISTINCT v.user_id),
        2
    ) as conversion_rate
FROM visitors v
LEFT JOIN registered r
  ON v.user_id = r.user_id;
```

**关键技术点**:
1. 使用 LEFT JOIN（保留所有访问用户）
2. 时间范围要一致（同一天的访问和注册）
3. 去重要正确
```

3. **添加到**: calculation_rules/conversion.md

## 📚 常见问题

### Q1: 必须填写所有字段吗？

**A**: 不是，但有必填项

**必填项**（必须填）:
- 名称、定义
- 口径（术语和指标）
- 分类规则（维度）
- SQL 实现

**推荐项**（建议填）:
- 别名、示例、关联关系

**可选项**（有就填）:
- 历史演变、常见误解

### Q2: 口径一定要写那么详细吗？

**A**: 是的，口径是最重要的！

**原因**:
- 口径决定了统计结果
- 口径不同，结果完全不同
- 口径模糊会导致理解不一致

**建议**:
- 8 个要素尽量都填
- 特别是统计对象、去重规则、包含/排除条件

### Q3: 如何写好示例？

**A**: 遵循"正反边"原则

- **正面示例**: 符合定义的情况（至少 2 个）
- **反面示例**: 不符合定义的情况（至少 2 个）
- **边界示例**: 容易混淆的边界情况（至少 1 个）

### Q4: 引用关系一定要用链接吗？

**A**: 强烈建议

**好处**:
- 点击可以跳转
- 修改时知道影响范围
- AI 可以追溯

**格式**:
```markdown
[术语名称](../glossary.md#术语名称)
[维度名称](../dimensions/xxx_dimensions.md#维度名称)
```

### Q5: 简单指标和复杂指标如何区分？

**A**: 看 SQL 复杂度

| 特征 | 简单指标 | 复杂指标 |
|------|---------|---------|
| 表数量 | 单表 | 多表 |
| SQL 行数 | < 20 行 | > 30 行 |
| JOIN | 不需要或简单 JOIN | 复杂 JOIN |
| 计算步骤 | 1-2 步 | 3+ 步 |
| 易错性 | 不易错 | 容易出错 |

**处理**:
- 简单指标: 只用 METRIC_TEMPLATE
- 复杂指标: METRIC_TEMPLATE + CALCULATION_TEMPLATE

## 🎯 总结

### 四类模板的关系

```
GLOSSARY_TEMPLATE (术语)
    ↓ 被引用
DIMENSION_TEMPLATE (维度)
    ↓ 被引用
METRIC_TEMPLATE (指标)
    ↓ 被引用（复杂指标）
CALCULATION_TEMPLATE (计算规则)
```

### 核心要点

1. **术语模板**: 重点是"口径"
2. **维度模板**: 重点是"分类规则"（互斥、穷尽）
3. **指标模板**: 重点是"引用关系"和"数据口径"
4. **计算规则模板**: 重点是"关键技术点"和"常见错误"

- ✅ 按顺序填写（术语 → 维度 → 指标 → 计算规则）

- ✅ 提供丰富的示例
- ✅ 明确引用关系
- ✅ 记录历史演变
