# 指标定义模板

> 本文档是指标定义的标准模板，定义了如何规范地添加和描述业务指标。

---

## 📋 模板说明

### 什么是指标？

**指标**是用于衡量业务状况的**量化度量**，是业务知识层的**核心表达**。

**特征**：
- ✅ 是可量化的业务度量（有数值）
- ✅ 组合术语和维度形成完整表达
- ✅ 有明确的计算规则
- ✅ 指向具体的数据来源

**不是什么**：
- ❌ 不是术语（术语是概念，指标是度量）
- ❌ 不是维度（维度是角度，指标是度量）

**示例**：
- ✅ "DAU（日活跃用户数）" - 是指标（可量化）
- ❌ "活跃用户" - 是术语（概念）
- ❌ "日" - 是维度（角度）

### 指标的组成

**指标 = 术语 + 维度 + 聚合方式**

```
示例: DAU (日活跃用户数)
  = 活跃用户（术语）
  + 日（维度）
  + 数量（聚合：COUNT）
  
示例: 次日留存率
  = 留存用户（术语）
  + 次日（维度）
  + 比率（聚合：除法）
```

### 为什么需要指标定义？

1. **统一口径** - 让所有人对同一指标有相同理解和计算方式
2. **指导 SQL 生成** - 告诉 AI 如何生成 SQL
3. **保证准确性** - 明确计算规则，避免错误
4. **建立标准** - 为数据分析提供标准化的度量

## 📖 字段详细说明

### 1. 指标类型

**常见类型**:

| 类型 | 说明 | 示例 |
|------|------|------|
| **基础指标** | 直接统计，不依赖其他指标 | DAU、新增用户数、发帖数 |
| **复合指标** | 由多个基础指标计算得出 | 活跃率 = DAU / 总用户数 |
| **比率指标** | 两个指标的比值 | 留存率、转化率、点击率 |
| **累计指标** | 累计值 | 累计注册用户数、累计交易额 |
| **平均指标** | 平均值 | 人均发帖数、平均停留时长 |

### 2. 计算公式

**怎么写**:
- ✅ 使用数学符号或伪代码
- ✅ 说明每个变量的含义
- ✅ 如果有条件，明确说明

**示例**:
```markdown
**计算公式**: 
```
次日留存率 = (D1活跃用户数 / D0新增用户数) × 100%

其中:
- D0新增用户数: 注册日当天的新增用户数
- D1活跃用户数: D0新增用户中，在D1有活跃行为的用户数
- D0: 注册日
- D1: 注册日 + 1天
```
```

### 3. 数据口径 ⭐最重要

**什么是"数据口径"？**

数据口径是指标统计的**具体规则**，决定了指标的数值。

**为什么口径是最重要的？**

```
例子: "DAU"

口径1: 统计登录过的用户
  → 结果: 100万

口径2: 统计有任意行为的用户  
  → 结果: 150万

口径3: 统计有发帖行为的用户
  → 结果: 10万

同一个指标名称，不同口径，结果差异巨大！
```

**口径必须明确的内容**：

1. **统计对象**
   - 统计的是什么？
   - 示例："user_id"、"post_id"

2. **聚合方式**
   - 如何聚合？COUNT/SUM/AVG/比率？
   - 示例："COUNT(DISTINCT user_id)"

3. **去重规则**
   - 如何去重？
   - 示例："按 user_id 去重，一个用户只计一次"

4. **时间粒度**
   - 按什么时间粒度统计？
   - 示例："按自然日统计"

5. **时间范围**
   - 时间如何界定？
   - 示例："按行为发生时间，自然日 00:00-23:59"

6. **包含条件**
   - 什么情况计入？
   - 示例："行为类型 IN (登录, 浏览, ...)"

7. **排除条件**
   - 什么情况排除？
   - 示例："排除测试账号"

8. **计算逻辑**
   - 详细的计算步骤
   - 如果有多个步骤，逐步说明

**完整示例**:
```markdown
**数据口径**:

**统计对象**: user_id（用户唯一标识）

**聚合方式**: COUNT(DISTINCT user_id) - 去重计数

**去重规则**: 按 user_id 去重，同一用户在统计日只计一次

**时间粒度**: 日（自然日）

**时间范围**: 按行为发生时间（behavior_time），自然日 00:00:00 - 23:59:59

**包含条件**: 
- 用户状态 = '正常'（is_active = 1）
- 行为类型 IN (登录, 浏览, 发帖, 评论, 点赞, 交易)
- 行为时间在统计日期内

**排除条件**: 
- 排除测试账号（user_type = 'test'）
- 排除内部账号（user_type = 'internal'）
- 排除机器人（user_type = 'bot'）

**计算逻辑**:
```
步骤1: 从用户行为表筛选符合条件的记录
  - 时间在统计日期内
  - 行为类型符合活跃定义
  - 排除测试账号

步骤2: 按 user_id 去重

步骤3: 计数
```
```

### 5. 计算规则

**简单指标** vs **复杂指标**:

| 类型 | 特征 | 处理方式 |
|------|------|---------|
| 简单指标 | 单表、简单聚合 | 直接在这里写 SQL |
| 复杂指标 | 多表、复杂逻辑 | 引用 calculation_rules/ |

**简单指标示例**（DAU）:
```markdown
**计算类型**: 简单计算

**SQL 逻辑** (Trino 语法):
```sql
SELECT 
    date,
    COUNT(DISTINCT user_id) as dau
FROM 
    dws_user_daily
WHERE 
    date = date_add('day', -1, current_date)
    AND is_active = 1
GROUP BY 
    date;
```

**关键点**:
- 使用 COUNT(DISTINCT) 去重
- 使用分区字段 date 筛选
- 使用 is_active 标识筛选活跃用户
```

**复杂指标示例**（次日留存率）:
```markdown
**计算类型**: 复杂计算

**详细计算规则**: 
见 [留存率计算规则](../calculation_rules/retention.md)

**关键技术点**:
- 需要关联注册表和行为表
- 必须使用 LEFT JOIN（不能用 INNER JOIN）
- 时间计算: date_add('day', 1, register_date)
- 分子分母都要 DISTINCT

**SQL 模板**:
```sql
-- 简化的 SQL 结构（完整版见 calculation_rules/retention.md）
WITH base_users AS (...),
     retention_users AS (...)
SELECT 
    COUNT(DISTINCT retention_users) / COUNT(DISTINCT base_users) * 100.0
FROM ...
```
```

## 📊 完整示例

### 示例 1: 简单指标 - DAU

```markdown
## DAU (Daily Active User) - 日活跃用户数

### 基本信息

**指标名称**: 日活跃用户数

**英文名称**: Daily Active User

**英文缩写**: DAU

**指标类型**: 基础指标

**别名**: 
- 日活
- 日活用户
- 日活跃

### 定义

**标准定义**: 
某自然日内有任意行为的去重用户数。

**业务含义**: 
DAU 是衡量平台日常活跃度的核心指标，反映了平台每天有多少用户在实际使用。DAU 的增长表示平台吸引力提升，DAU 的下降需要分析原因。

**计算公式**: 
```
DAU = COUNT(DISTINCT user_id)
WHERE 行为发生日期 = 统计日期
  AND 符合"活跃用户"定义
```

### 引用关系

**引用的术语**:
- [活跃用户](../glossary.md#活跃用户) - 定义了什么行为算"活跃"

**引用的维度**:
- [日](../dimensions/time_dimensions.md#日) - 定义了时间粒度

**引用的其他指标**:
- 无（基础指标，不依赖其他指标）

### 数据口径

**统计对象**: user_id（用户唯一标识）

**聚合方式**: COUNT(DISTINCT user_id) - 去重计数

**去重规则**: 按 user_id 去重，同一用户在统计日只计一次

**时间粒度**: 日（自然日）

**时间范围**: 按行为发生时间（behavior_time），自然日 00:00:00 - 23:59:59

**包含条件**: 
- 用户状态 = '正常'（is_active = 1）
- 行为类型 IN (登录, 浏览, 发帖, 评论, 点赞, 交易, 搜索)
- 行为时间在统计日期内

**排除条件**: 
- 排除测试账号（user_type = 'test'）
- 排除内部账号（user_type = 'internal'）
- 排除机器人（user_type = 'bot'）

**计算逻辑**:
```
步骤1: 从用户行为表或汇总表获取数据
步骤2: 筛选统计日期的数据
步骤3: 筛选活跃用户（is_active = 1）
步骤4: 按 user_id 去重计数
```

### 数据来源

**推荐数据表**: 
- **表名**: dws_user_daily
- **字段**: date, dau（或 user_id + is_active）
- **选择理由**: 
  - 汇总表，查询速度快（< 1秒）
  - 已预计算 DAU，可直接使用
  - T+1 更新，数据完整
  - 适合日常监控和报表

**备选数据表**: 
- **表名**: dwd_user_behavior
- **字段**: user_id, behavior_time, behavior_type, date
- **选择理由**: 
  - 明细表，灵活性高
  - 可以自定义活跃行为类型
  - 可以添加更多筛选条件（如特定行为）
- **使用场景**: 
  - 需要自定义活跃定义时
  - 需要按特定行为类型统计时
  - 需要实时数据时（汇总表 T+1）

**关联表**:
- 不需要关联其他表（单表即可）

### 计算规则

**计算类型**: 简单计算

**SQL 逻辑** (Trino 语法):

**方案1: 使用汇总表（推荐）**
```sql
-- 如果汇总表中有预计算的 dau 字段
SELECT 
    date,
    dau
FROM 
    dws_user_daily
WHERE 
    date = date_add('day', -1, current_date)  -- 昨天
ORDER BY 
    date;
```

**方案2: 从明细表计算**
```sql
-- 从用户行为明细表计算
SELECT 
    date,
    COUNT(DISTINCT user_id) as dau
FROM 
    dwd_user_behavior
WHERE 
    date = date_add('day', -1, current_date)
    AND user_type NOT IN ('test', 'internal', 'bot')  -- 排除条件
GROUP BY 
    date;
```

**关键点**:
- 使用 COUNT(DISTINCT) 去重
- 必须包含分区字段 date 的筛选
- 使用 Trino 的 date_add 函数

### 使用场景

**适合场景**:
- ✅ 日常运营监控（每日查看 DAU）
- ✅ 趋势分析（观察 DAU 的增长趋势）
- ✅ 同比/环比分析（与昨天、去年同期对比）
- ✅ 异常检测（发现 DAU 异常波动）
- ✅ 渠道效果评估（对比不同渠道的 DAU）

**不适合场景**:
- ❌ 实时监控（汇总表 T+1 更新，有延迟）
- ❌ 小时级分析（DAU 是日粒度，不支持小时）

**典型问题**:
- "昨天的 DAU 是多少？"
- "最近 7 天的 DAU 趋势如何？"
- "这个月的 DAU 比上个月增长了多少？"
- "iOS 和 Android 的 DAU 对比"

### 解读说明

**数值范围**: 
- 正常范围: 100万 - 200万（根据实际业务调整）
- 异常范围: < 80万 或 > 250万

**数值含义**:
- **数值上升**: 
  - 好现象：用户活跃度提升，平台吸引力增强
  - 可能原因：新功能上线、运营活动、外部事件
- **数值下降**: 
  - 需要关注：用户活跃度下降
  - 可能原因：产品问题、竞品冲击、节假日、数据异常

**影响因素**:
- 节假日：周末和节假日通常较低
- 运营活动：活动期间会提升
- 产品更新：新功能可能带来波动
- 外部事件：市场行情、热点事件
- 数据质量：埋点问题、数据延迟

**对比基准**:
- 同比：与去年同期对比（消除季节性影响）
- 环比：与昨天对比（观察短期变化）
- 目标值：月度/季度的 DAU 目标

### 注意事项

**数据时效性**:
- 更新频率：T+1 日更新（每天凌晨更新前一天数据）
- 数据延迟：当天数据需要等到次日才完整
- 实时性：如需实时数据，使用明细表

**数据质量**:
- 注意异常值：突然暴涨可能是刷量
- 注意缺失：数据未更新会导致 DAU 为 0
- 注意去重：确保使用 DISTINCT

**计算限制**:
- 需要有用户行为数据
- 需要有用户 ID
- 依赖埋点的准确性

**常见错误**:
- ❌ 忘记去重：COUNT(user_id) 而不是 COUNT(DISTINCT user_id)
- ❌ 忘记分区条件：导致全表扫描
- ❌ 包含测试账号：导致数值虚高
- ❌ 时间范围错误：统计了错误的日期

### 示例 2: 复杂指标 - 次日留存率

```markdown
## 次日留存率 (D1 Retention Rate)

### 基本信息

**指标名称**: 次日留存率

**英文名称**: Day 1 Retention Rate

**英文缩写**: D1 RR

**指标类型**: 比率指标

**别名**: 
- 次留
- D1 留存
- 新用户次日留存

### 定义

**标准定义**: 
某日新增的用户中，在次日（D1）仍然活跃的用户占比。

**业务含义**: 
次日留存率是评估产品留存能力的关键指标，反映了新用户对产品的初步认可度。高次留表示产品有吸引力，低次留需要优化新手体验。

**计算公式**: 
```
次日留存率 = (D1活跃用户数 / D0新增用户数) × 100%

其中:
- D0: 注册日（基准日）
- D1: 注册日 + 1天
- D0新增用户数: 在 D0 注册的用户数
- D1活跃用户数: D0新增用户中，在 D1 有活跃行为的用户数
```

### 引用关系

**引用的术语**:
- [新增用户](../glossary.md#新增用户) - 作为基准用户（分母）
- [活跃用户](../glossary.md#活跃用户) - 判断是否留存（分子）
- [留存用户](../glossary.md#留存用户) - 留存的定义

**引用的维度**:
- [日](../dimensions/time_dimensions.md#日) - 时间粒度
- D0/D1 的时间关系

**引用的其他指标**:
- [新增用户数](user_metrics.md#新增用户数) - 作为分母
- 需要判断用户是否活跃（引用活跃用户的定义）

### 数据口径

**统计对象**: user_id（用户唯一标识）

**聚合方式**: 比率计算（分子 / 分母 × 100%）

**去重规则**: 
- 分母：按 user_id 去重（D0 新增用户）
- 分子：按 user_id 去重（D1 活跃用户）

**时间粒度**: 日（按注册日期分组）

**时间范围**: 
- D0: 注册日期（register_date）
- D1: 注册日期 + 1天（date_add('day', 1, register_date)）

**包含条件**: 
- **分母**（D0 新增用户）:
  - 注册时间在 D0 日期内
  - 注册状态 = '成功'
- **分子**（D1 活跃用户）:
  - 是 D0 的新增用户
  - 在 D1 有活跃行为（符合活跃用户定义）

**排除条件**: 
- 排除测试账号
- 排除注册未完成的用户

**计算逻辑**:
```
步骤1: 找到 D0 的新增用户（基准用户）
  - 从注册表筛选 D0 注册的用户
  - 记录 user_id 和 register_date

步骤2: 找到这些用户在 D1 的活跃记录
  - 关联行为表
  - 筛选 D1 日期的行为
  - 有行为记录 = 留存

步骤3: 计算留存率
  - 分子: COUNT(DISTINCT D1活跃的user_id)
  - 分母: COUNT(DISTINCT D0新增的user_id)
  - 留存率 = 分子 / 分母 × 100%
```

### 数据来源

**推荐数据表**: 
- **表1**: dwd_user_register（获取 D0 新增用户）
  - 字段: user_id, register_date
- **表2**: dwd_user_behavior（获取 D1 活跃数据）
  - 字段: user_id, date, behavior_type
- **关联方式**: LEFT JOIN（重要！）

**备选数据表**: 
- **表**: dws_user_daily（如果有预计算的留存标识）
  - 字段: user_id, date, is_d1_retention
  - 使用场景: 快速查询，但灵活性低

**关联表**:
```sql
FROM dwd_user_register r
LEFT JOIN dwd_user_behavior b
  ON r.user_id = b.user_id
  AND b.date = date_add('day', 1, r.register_date)
```

### 计算规则

**计算类型**: 复杂计算

**详细计算规则**: 
见 [留存率计算规则](../calculation_rules/retention.md)

**关键技术点**:
1. **必须使用 LEFT JOIN**
   - 原因: 保留所有 D0 新增用户（包括未留存的）
   - 错误: 使用 INNER JOIN 会遗漏未留存用户，导致分母变小，留存率虚高

2. **时间计算要精确**
   - D1 = date_add('day', 1, register_date)
   - 不能用范围（>= 和 <=），要精确到天

3. **去重要正确**
   - 分子: COUNT(DISTINCT retention_users.user_id)
   - 分母: COUNT(DISTINCT base_users.user_id)

4. **类型转换**
   - 除法前转换为 DOUBLE: CAST(分子 AS DOUBLE)
   - 避免整数除法丢失精度

**SQL 模板**:
```sql
-- 完整 SQL 见 calculation_rules/retention.md
-- 这里是简化结构

WITH base_users AS (
    -- D0 新增用户
    SELECT user_id, register_date
    FROM dwd_user_register
    WHERE register_date = date '2024-01-01'
),
retention_users AS (
    -- D1 活跃用户
    SELECT bu.user_id
    FROM base_users bu
    INNER JOIN dwd_user_behavior ub
      ON bu.user_id = ub.user_id
      AND ub.date = date_add('day', 1, bu.register_date)
)
SELECT 
    ROUND(
        CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
        / COUNT(DISTINCT bu.user_id), 
        2
    ) as retention_rate
FROM base_users bu
LEFT JOIN retention_users ru
  ON bu.user_id = ru.user_id;
```

### 使用场景

**适合场景**:
- ✅ 评估产品留存能力
- ✅ 评估渠道质量（不同渠道的留存率对比）

### 解读说明

**数值范围**: 
- 优秀: > 40%
- 良好: 30% - 40%
- 一般: 20% - 30%
- 较差: < 20%
（根据行业和产品类型调整）

**数值含义**:
- **留存率高**: 
  - 产品有吸引力，用户愿意回来
  - 新手体验好
  - 内容或功能有价值
- **留存率低**: 
  - 需要优化新手引导
  - 内容或功能不够吸引人
  - 可能有产品问题

**影响因素**:
- 产品体验：新手引导、核心功能
- 内容质量：首页推荐、内容丰富度
- 用户质量：不同渠道用户质量不同
- 外部因素：市场环境、竞品

**对比基准**:

- 环比：与上月对比
- 渠道对比：不同渠道的留存率
- 行业基准：同行业的平均水平

### 注意事项

**数据时效性**:
- 更新频率：T+2（需要等到 D1 结束）
- 数据延迟：1月1日注册的用户，1月3日才能看到完整的次留
- 实时性：无法实时查看，必须等待

**数据质量**:
- D1 数据必须完整（等到 D1 日结束）
- 注册数据和行为数据都要准确
- 注意时区一致性

**计算限制**:
- 需要有注册数据和行为数据
- 需要等待 D1 结束
- 计算量较大（需要关联两张表）

**常见错误**:
- ❌ 使用 INNER JOIN：遗漏未留存用户，留存率虚高
- ❌ 时间计算错误：统计的不是 D1
- ❌ 没有去重：重复计数
- ❌ 整数除法：精度丢失
