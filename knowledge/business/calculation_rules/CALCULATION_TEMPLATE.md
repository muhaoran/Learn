# 计算规则模板

> 本文档是计算规则的标准模板，定义了如何规范地添加和描述复杂指标的计算方法。

---

## 📋 模板说明

### 什么是计算规则？

**计算规则**是复杂指标的**详细计算方法和实现指导**，是业务知识层的**实现层**。

**特征**：
- ✅ 提供详细的计算步骤
- ✅ 提供完整的 SQL 模板
- ✅ 说明关键技术点和常见错误
- ✅ 引用术语、维度、指标
- ✅ 提供变体场景的处理方法

**不是什么**：
- ❌ 不是简单指标的定义（简单指标直接在 metrics/ 中定义）
- ❌ 不是术语或维度的定义
- ❌ 不是具体的 SQL 案例（案例在 sql_examples/ 中）

**什么时候需要计算规则？**

| 指标复杂度 | 是否需要计算规则 | 示例 |
|-----------|----------------|------|
| 简单指标 | ❌ 不需要 | DAU（单表、简单聚合） |
| 中等复杂 | ⚠️ 可选 | 活跃率（两个指标相除） |
| 复杂指标 | ✅ 需要 | 次日留存率（多表、复杂逻辑） |

**判断标准**：
- 需要多表关联 → 需要计算规则
- 有复杂的时间计算 → 需要计算规则
- 有多个计算步骤 → 需要计算规则
- 有常见的计算错误 → 需要计算规则
- 有多种变体场景 → 需要计算规则

### 为什么需要计算规则？

1. **提供实现指导** - 告诉 AI 如何生成复杂 SQL
2. **避免常见错误** - 标注容易出错的地方
3. **保证准确性** - 详细的步骤保证计算正确
4. **支持变体** - 提供不同场景的处理方法

### 计算公式

> **什么是"计算公式"？**
> 
> 计算公式是指标的**数学表达式**，用符号和变量表示计算逻辑。
> 
> **要求**：
> - 使用标准的数学符号
> - 定义所有变量
> - 说明计算顺序
> - 处理边界情况（如除零）

**数学公式**:
```
[指标名称] = [数学表达式]

其中:
- [变量1]: [定义和说明]
- [变量2]: [定义和说明]
- [变量3]: [定义和说明]

特殊情况:
- 当 [条件] 时: [如何处理]
- 当 [条件] 时: [如何处理]
```

**示例**:
```
次日留存率 = (D1活跃用户数 / D0新增用户数) × 100%

其中:
- D0: 注册日（基准日）
- D1: 注册日 + 1天
- D0新增用户数: 在 D0 注册的去重用户数
- D1活跃用户数: D0新增用户中，在 D1 有活跃行为的去重用户数

特殊情况:
- 当 D0新增用户数 = 0 时: 留存率 = 0 或 NULL
- 当 D1 数据未完整时: 不计算，等待数据完整
```

**示例**:
```markdown
**技术点1**: JOIN 类型选择

- **说明**: 
  计算留存率时，必须使用 LEFT JOIN 而不是 INNER JOIN
  
- **正确做法**: 
  ```sql
  FROM base_users bu
  LEFT JOIN retention_users ru
    ON bu.user_id = ru.user_id
  ```
  
- **错误做法**: 
  ```sql
  FROM base_users bu
  INNER JOIN retention_users ru  -- ❌ 错误
    ON bu.user_id = ru.user_id
  ```
  
- **影响**: 
  使用 INNER JOIN 会遗漏未留存的用户，导致：
  - 分母变小（只统计了留存的用户）
  - 留存率虚高（可能从 30% 变成 100%）
  - 结果完全错误
```

```markdown

|------|------|------|---------|

**模板代码** (Trino 语法):
```sql
-- ============================================
-- [计算规则名称]
-- 业务含义: [一句话说明]
-- 适用指标: [指标列表]
-- 复杂度: [复杂度级别]
-- ============================================

-- 参数说明（如果有参数需要替换）
-- @param start_date: 开始日期，如 '2024-01-01'
-- @param end_date: 结束日期，如 '2024-01-31'

-- ============================================
-- 步骤1: [第一步的说明]
-- ============================================
WITH step1 AS (
    SELECT 
        [字段1],
        [字段2],
        [字段3]
    FROM 
        [表名]
    WHERE 
        -- 分区条件（必须）
        [分区字段] >= [开始时间]
        AND [分区字段] < [结束时间]
        
        -- 业务条件
        AND [条件1]
        AND [条件2]
),

-- ============================================
-- 步骤2: [第二步的说明]
-- ============================================
step2 AS (
    SELECT 
        [字段1],
        [字段2]
    FROM 
        step1
    [JOIN/WHERE/...]
),

-- ============================================
-- 步骤3: [第三步的说明]
-- ============================================
step3 AS (
    SELECT 
        s1.[字段],
        s2.[字段]
    FROM 
        step1 s1
    [LEFT/INNER] JOIN  -- [说明为什么用这种 JOIN]
        step2 s2
    ON 
        s1.[关联字段] = s2.[关联字段]
        AND [其他关联条件]
)

-- ============================================
-- 最终计算: [最终计算的说明]
-- ============================================
SELECT 
    [维度字段],
    
    -- 分子
    COUNT(DISTINCT [字段1]) as [分子名称],
    
    -- 分母
    COUNT(DISTINCT [字段2]) as [分母名称],
    
    -- 最终指标
    ROUND(
        CAST(COUNT(DISTINCT [字段1]) AS DOUBLE) * 100.0 
        / NULLIF(COUNT(DISTINCT [字段2]), 0),  -- 避免除零
        2  -- 保留2位小数
    ) as [指标名称]
    
FROM 
    step3
GROUP BY 
    [维度字段]
ORDER BY 
    [排序字段];
```

5. 保持注释的完整性

> - 边界情况测试

**验证步骤**:

**步骤1: 数值合理性检查**
- [ ] 数值在合理范围内？

- [ ] 比率指标在 0-100% 之间？

**步骤2: 逻辑正确性检查**

- [ ] 分母为 0 时如何处理？

- [ ] 极端情况（全部留存/全部流失）是否正确？

- [ ] 与历史数据对比，是否在合理范围？
- [ ] 与其他相关指标对比，是否一致？

**业务价值**: 
- 评估产品对新用户的吸引力
- 评估不同渠道的用户质量
- 指导产品优化方向
- 预测用户生命周期价值

**常见场景**: 
- 每日监控新用户的次日留存率
- 对比不同渠道的留存率
- 评估新功能对留存的影响
- A/B 测试效果评估

### 引用关系

**引用的术语**:
- [新增用户](../glossary.md#新增用户) - 作为基准用户（分母）
- [活跃用户](../glossary.md#活跃用户) - 判断是否留存（分子）
- [留存用户](../glossary.md#留存用户) - 留存的定义

**引用的维度**:
- [日](../dimensions/time_dimensions.md#日) - 时间粒度
- D0/D1 的时间关系

**引用的指标**:
- [新增用户数](../metrics/user_metrics.md#新增用户数) - 分母
- 需要判断用户是否活跃（引用活跃用户的定义）

### 计算公式

**数学公式**:
```
次日留存率 = (D1活跃用户数 / D0新增用户数) × 100%

其中:
- D0: 注册日（基准日）
- D1: 注册日 + 1天（次日）
- D0新增用户数: 在 D0 注册的去重用户数
- D1活跃用户数: D0新增用户中，在 D1 有活跃行为的去重用户数

特殊情况:
- 当 D0新增用户数 = 0 时: 留存率 = NULL（无法计算）
- 当 D1 数据未完整时: 不计算，等待数据完整
```

### 计算步骤

**步骤1**: 获取 D0 新增用户（基准用户）

- **输入**: dwd_user_register 表
- **操作**: 筛选指定日期注册的用户
- **输出**: user_id, register_date 列表
- **SQL 片段**:
  ```sql
  WITH base_users AS (
      SELECT 
          user_id,
          cast(register_time as date) as register_date
      FROM 
          dwd_user_register
      WHERE 
          register_date = date '2024-01-01'  -- D0
  )
  ```

**步骤2**: 找到 D1 活跃的用户（留存用户）

- **输入**: 步骤1 的 base_users + dwd_user_behavior 表
- **操作**: 
  - 关联行为表
  - 筛选 D1 日期的行为
  - 有行为记录 = 留存
- **输出**: 留存的 user_id 列表
- **SQL 片段**:
  ```sql
  retention_users AS (
      SELECT 
          bu.user_id,
          bu.register_date
      FROM 
          base_users bu
      INNER JOIN 
          dwd_user_behavior ub
      ON 
          bu.user_id = ub.user_id
          -- 关键: D1 = D0 + 1天
          AND ub.date = date_add('day', 1, bu.register_date)
  )
  ```

**步骤3**: 计算留存率

- **输入**: base_users + retention_users
- **操作**: 
  - 使用 LEFT JOIN 关联
  - 计算分子（留存用户数）
  - 计算分母（新增用户数）
  - 计算比率
- **输出**: 留存率
- **SQL 片段**:
  ```sql
  SELECT 
      COUNT(DISTINCT bu.user_id) as base_count,      -- 分母
      COUNT(DISTINCT ru.user_id) as retention_count, -- 分子
      ROUND(
          CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
          / COUNT(DISTINCT bu.user_id), 
          2
      ) as retention_rate
  FROM 
      base_users bu
  LEFT JOIN  -- 必须用 LEFT JOIN
      retention_users ru
  ON 
      bu.user_id = ru.user_id
  ```

### SQL 模板

**完整 SQL** (Trino 语法):
```sql
-- ============================================
-- 次日留存率计算
-- 业务含义: 计算新增用户在注册次日的回访率
-- 适用指标: 次日留存率
-- 复杂度: 非常复杂 ⭐⭐⭐⭐⭐
-- ============================================

-- 参数说明
-- @param register_date: 注册日期，如 date '2024-01-01'

-- ============================================
-- 步骤1: 获取 D0 新增用户（基准用户）
-- ============================================
WITH base_users AS (
    SELECT 
        user_id,
        cast(register_time as date) as register_date
    FROM 
        dwd_user_register
    WHERE 
        -- 分区条件（必须）
        register_date = date '2024-01-01'  -- @param
        
        -- 业务条件
        AND register_status = 'success'  -- 注册成功
        AND user_type NOT IN ('test', 'internal')  -- 排除测试和内部账号
),

-- ============================================
-- 步骤2: 找到 D1 活跃的用户（留存用户）
-- ============================================
retention_users AS (
    SELECT 
        bu.user_id,
        bu.register_date
    FROM 
        base_users bu
    INNER JOIN 
        dwd_user_behavior ub
    ON 
        bu.user_id = ub.user_id
        -- 关键: D1 = D0 + 1天（Trino 语法）
        AND ub.date = date_add('day', 1, bu.register_date)
    
    -- 可选: 如果需要特定行为类型
    -- WHERE ub.behavior_type IN ('login', 'view', 'post')
)

-- ============================================
-- 步骤3: 计算留存率
-- ============================================
SELECT 
    bu.register_date,
    
    -- 分母: D0 新增用户数
    COUNT(DISTINCT bu.user_id) as new_users_count,
    
    -- 分子: D1 活跃用户数
    COUNT(DISTINCT ru.user_id) as retention_users_count,
    
    -- 留存率
    ROUND(
        CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
        / NULLIF(COUNT(DISTINCT bu.user_id), 0),  -- 避免除零
        2  -- 保留2位小数
    ) as retention_rate
    
FROM 
    base_users bu
LEFT JOIN  -- ⚠️ 必须用 LEFT JOIN，不能用 INNER JOIN
    retention_users ru
ON 
    bu.user_id = ru.user_id
    AND bu.register_date = ru.register_date
GROUP BY 
    bu.register_date
ORDER BY 
    bu.register_date;
```

### 关键技术点详解

**技术点1**: JOIN 类型选择 ⭐最重要

**问题**: 
计算留存率时，必须保留所有基准用户（包括未留存的），才能得到正确的分母。

**正确做法**:
```sql
FROM base_users bu
LEFT JOIN retention_users ru
  ON bu.user_id = ru.user_id
```
**说明**: 
- LEFT JOIN 保留 base_users 的所有记录
- 即使用户未留存（ru.user_id 为 NULL），也会保留在结果中
- 分母 = 所有基准用户
- 分子 = 有匹配的留存用户

**错误做法**:
```sql
FROM base_users bu
INNER JOIN retention_users ru  -- ❌ 错误
  ON bu.user_id = ru.user_id
```
**说明**: 
- INNER JOIN 只保留两边都有的记录
- 未留存的用户被过滤掉了
- 分母 = 只有留存的用户（错误！）

**后果**:
- 分母变小（只统计了留存的用户）
- 留存率虚高（可能从 30% 变成 100%）
- 结果完全错误，误导决策

**技术点2**: 时间计算方法

**问题**: 
D1 必须是 D0 + 1天，不能用范围查询。

**正确做法**:
```sql
AND ub.date = date_add('day', 1, bu.register_date)
```
**说明**: 
- 精确计算 D1 日期
- 使用 Trino 的 date_add 函数
- 每个用户的 D1 是相对于其注册日期

**错误做法**:
```sql
-- 错误1: 使用固定日期
AND ub.date = date '2024-01-02'  -- ❌ 错误

-- 错误2: 使用范围
AND ub.date >= bu.register_date 
AND ub.date <= date_add('day', 1, bu.register_date)  -- ❌ 错误
```

**后果**:
- 错误1: 只能计算特定日期的留存，不通用
- 错误2: 可能包含 D0 和 D2 的数据，不是 D1

**技术点3**: 去重位置和方式

**问题**: 
分子和分母都需要去重，且去重位置很重要。

**正确做法**:
```sql
COUNT(DISTINCT bu.user_id) as new_users_count,      -- 分母去重
COUNT(DISTINCT ru.user_id) as retention_users_count -- 分子去重
```
**说明**: 
- 在最终 SELECT 中去重
- 分子分母分别去重
- 使用 DISTINCT 避免重复计数

**错误做法**:
```sql
-- 错误: 不去重
COUNT(bu.user_id)  -- ❌ 可能重复计数
```

**后果**:
- 如果用户有多条记录，会重复计数
- 分子分母都可能虚高
- 留存率不准确

**技术点4**: 类型转换和精度

**问题**: 
除法运算需要注意类型和精度。

**正确做法**:
```sql
ROUND(
    CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
    / NULLIF(COUNT(DISTINCT bu.user_id), 0),
    2
)
```
**说明**: 
- CAST AS DOUBLE: 转换为浮点数
- * 100.0: 转换为百分比
- NULLIF(..., 0): 避免除零错误
- ROUND(..., 2): 保留2位小数

**错误做法**:
```sql
-- 错误1: 整数除法
COUNT(ru.user_id) / COUNT(bu.user_id) * 100  -- ❌ 精度丢失

-- 错误2: 不处理除零
COUNT(ru.user_id) / COUNT(bu.user_id)  -- ❌ 可能除零错误
```

**后果**:
- 错误1: 整数除法，小数部分丢失（如 0.3 变成 0）
- 错误2: 分母为 0 时报错

### 常见错误详解

**错误1**: 使用 INNER JOIN

**错误表现**:
```sql
FROM base_users bu
INNER JOIN retention_users ru  -- ❌
  ON bu.user_id = ru.user_id
```

**问题分析**:
- INNER JOIN 只保留两边都有的记录
- 未留存的用户（ru.user_id 为 NULL）被过滤掉
- 导致分母只包含留存的用户

**后果**:
- 假设 D0 新增 100 人，D1 活跃 30 人
- 正确: 30 / 100 = 30%
- 错误: 30 / 30 = 100%（分母错误）

**正确写法**:
```sql
FROM base_users bu
LEFT JOIN retention_users ru  -- ✅
  ON bu.user_id = ru.user_id
```

**如何避免**:
- 记住：计算留存率必须用 LEFT JOIN
- 原因：需要保留所有基准用户
- 验证：检查分母是否等于 D0 新增用户数

**错误2**: 时间计算错误

**错误表现**:
```sql
-- 错误: 使用 D0 的日期
AND ub.date = bu.register_date  -- ❌

-- 错误: 使用固定日期
AND ub.date = date '2024-01-02'  -- ❌
```

**问题分析**:
- 错误1: 统计的是 D0 而不是 D1
- 错误2: 只能计算特定日期，不通用

**后果**:
- 错误1: 计算的是 D0 留存率（100%），不是 D1
- 错误2: 只能计算 2024-01-01 注册的用户，其他日期无法使用

**正确写法**:
```sql
AND ub.date = date_add('day', 1, bu.register_date)  -- ✅
```

**如何避免**:
- 使用 date_add 函数计算相对日期
- 每个用户的 D1 是相对于其注册日期
- 验证：检查 D1 日期是否等于 D0 + 1天

**错误3**: 忘记去重

**错误表现**:
```sql
COUNT(bu.user_id) as new_users_count  -- ❌ 没有 DISTINCT
```

**问题分析**:
- 如果用户有多条注册记录，会重复计数
- 如果 JOIN 产生多条记录，会重复计数

**后果**:
- 分子分母都可能虚高
- 留存率不准确

**正确写法**:
```sql
COUNT(DISTINCT bu.user_id) as new_users_count  -- ✅
COUNT(DISTINCT ru.user_id) as retention_users_count  -- ✅
```

**如何避免**:
- 统计用户数时，始终使用 DISTINCT
- 验证：检查去重前后的数值差异

### 变体场景

**变体1**: 按渠道分组的次日留存率

- **需求变化**: 需要对比不同渠道的留存率
  
- **SQL 调整**: 
  1. base_users 中添加 register_channel
  2. retention_users 中添加 register_channel
  3. SELECT 中添加 register_channel
  4. GROUP BY 添加 register_channel
  5. LEFT JOIN 的 ON 条件添加 register_channel
  
- **完整 SQL**:
  ```sql
  WITH base_users AS (
      SELECT 
          user_id,
          cast(register_time as date) as register_date,
          register_channel  -- 新增
      FROM dwd_user_register
      WHERE register_date = date '2024-01-01'
  ),
  retention_users AS (
      SELECT 
          bu.user_id,
          bu.register_date,
          bu.register_channel  -- 新增
      FROM base_users bu
      INNER JOIN dwd_user_behavior ub
        ON bu.user_id = ub.user_id
        AND ub.date = date_add('day', 1, bu.register_date)
  )
  SELECT 
      bu.register_channel,  -- 新增
      COUNT(DISTINCT bu.user_id) as new_users,
      COUNT(DISTINCT ru.user_id) as retention_users,
      ROUND(
          CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
          / COUNT(DISTINCT bu.user_id), 
          2
      ) as retention_rate
  FROM base_users bu
  LEFT JOIN retention_users ru
    ON bu.user_id = ru.user_id
    AND bu.register_channel = ru.register_channel  -- 新增
  GROUP BY 
      bu.register_channel  -- 新增
  ORDER BY 
      bu.register_channel;
  ```

**变体2**: 7日留存率

- **需求变化**: 计算 D7 留存而不是 D1
  
- **SQL 调整**: 
  只需修改一处：
  ```sql
  -- D1 留存
  AND ub.date = date_add('day', 1, bu.register_date)
  
  -- D7 留存
  AND ub.date = date_add('day', 7, bu.register_date)  -- 改为 7
  ```

**变体3**: 留存曲线（D1, D3, D7, D15, D30）

- **需求变化**: 一次性计算多个留存天数
  
- **SQL 调整**: 
  使用 UNION ALL 或窗口函数
  ```sql
  -- 方案1: UNION ALL
  SELECT 1 as day_n, ... WHERE date = date_add('day', 1, ...)
  UNION ALL
  SELECT 3 as day_n, ... WHERE date = date_add('day', 3, ...)
  UNION ALL

  ...
  ```

### 性能优化

**数据量评估**:
- dwd_user_register: 约 5万行/天（新增用户）
- dwd_user_behavior: 约 5000万行/天（用户行为）
- JOIN 后: 约 500万行（每个新增用户平均 100 条行为）

**优化建议**:

1. **表选择**: 
   - 优先使用 dwd_user_behavior（明细表）
   - 如果有预计算的留存表，使用汇总表

2. **分区裁剪**: 
   - register_date 必须在 WHERE 中
   - behavior date 必须在 JOIN 条件中

3. **提前过滤**: 
   - 在 base_users CTE 中就排除测试账号
   - 减少后续 JOIN 的数据量

4. **时间范围限制**:
   - 推荐: 查询单日或单月的留存
   - 警告: 查询超过 3 个月会较慢
   - 禁止: 不要查询超过 1 年的数据

**预计执行时间**:
- 单日留存: 10-30 秒
- 单月留存: 1-3 分钟
- 3个月留存: 5-10 分钟

### 数据质量要求

**必需数据**:
- dwd_user_register: 必须有完整的注册数据
- dwd_user_behavior: 必须有 D1 的行为数据

**数据完整性**:
- D0 的注册数据必须完整
- D1 的行为数据必须完整（等到 D1 日结束）
- 不能有数据缺失

**数据准确性**:
- 注册时间必须准确
- 行为时间必须准确
- user_id 必须一致（注册表和行为表）

**数据时效性**:
- T+2 更新（需要等到 D1 结束）
- 1月1日注册的用户，1月3日才能看到完整的次留

## 🔧 使用说明

### 对于人工填写

1. 确认需要创建计算规则（复杂指标）
2. 复制本模板
3. 按照字段说明填写
4. **特别注意**：
   - SQL 模板必须完整可执行
   - 关键技术点必须说明"为什么"
   - 常见错误必须说明"后果"
5. 使用检查清单自检
6. 提供至少 2 个变体场景

### 对于 AI 处理

AI 在处理原始资料或生成计算规则时，会：
1. 识别复杂指标
2. 分解计算步骤
3. 按照本模板组织内容
4. 生成完整的 SQL 模板（Trino 语法）
5. 标注关键技术点
6. 从 SQL 纠错记录中提取常见错误
7. 提供变体场景

### 什么时候创建计算规则？

**需要创建**:
- ✅ 需要多表关联
- ✅ 有复杂的时间计算
- ✅ 有多个计算步骤
- ✅ 有常见的计算错误
- ✅ 有多种变体场景
- ✅ SQL 超过 30 行

**不需要创建**:
- ❌ 单表简单聚合（如 COUNT、SUM）
- ❌ SQL 少于 20 行
- ❌ 没有特殊的技术要求
