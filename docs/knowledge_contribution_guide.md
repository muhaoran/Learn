# 知识库贡献指南

> 本文档指导如何向 ChatBI 知识库贡献内容。

---

## 为什么要贡献

- 提高 ChatBI 的准确率
- 支持更多业务场景
- 减少重复性工作
- 沉淀团队知识

---

## 贡献类型

### 1. 补充业务术语

**适用场景**: 
- 发现 AI 不理解某个业务术语
- 有新的业务概念

**贡献方式**:
1. 打开 `knowledge/business/glossary.md`
2. 按照模板添加术语定义
3. 包括: 标准名称、别名、定义、数据口径

**示例**:
```markdown
### 深度活跃用户

**标准名称**: 深度活跃用户

**别名/黑话**:
- 深度活跃
- 高活用户

**定义**:
在统计周期内，活跃天数 ≥ 20 天的用户。

**数据口径**:
- 统计对象: user_id
- 活跃定义: 同"活跃用户"定义
- 统计周期: 通常为自然月

**相关指标**:
- 深度活跃用户数
- 深度活跃率
```

### 2. 补充指标定义

**适用场景**:
- 有新的数据指标
- 现有指标定义不清晰

**贡献方式**:
1. 打开对应的指标文档（如 `knowledge/business/metrics/user_metrics.md`）
2. 按照模板添加指标定义
3. 包括: 定义、计算规则、数据口径、使用场景

**示例**:
```markdown
## 用户活跃率

### 定义
活跃用户占总用户的比例。

### 计算规则
```
活跃率 = DAU / 总用户数 * 100%
```

### 数据口径
- 分子: 当日活跃用户数（去重）
- 分母: 截至当日的累计注册用户数

### 数据来源
- DAU: `dws_user_daily`
- 总用户数: `dim_user` 或 `dws_user_daily`

### 使用场景
- 评估产品粘性
- 对比不同时期的用户活跃度
```

### 3. 补充数据表文档

**适用场景**:
- 有新的数据表
- 现有表文档不完整

**贡献方式**:
1. 复制 `knowledge/data_assets/tables/TABLE_TEMPLATE.md`
2. 重命名为表名（如 `dws_user_weekly.md`）
3. 填充表信息
4. 放到对应的目录（ods/dwd/dws/ads）

**必须包含**:
- 表的基本信息
- 字段列表（字段名、类型、含义、示例值）
- 使用场景
- 注意事项

### 4. 补充 SQL 案例

**适用场景**:
- 有新的需求类型
- 有经典的 SQL 值得分享

**贡献方式**:
1. 复制 `knowledge/sql_examples/EXAMPLE_TEMPLATE.md`
2. 重命名为案例名称
3. 填充案例信息
4. 放到对应的分类目录

**必须包含**:
- 业务需求（原始）
- 需求澄清过程
- SQL 语句（带注释）
- 技术方案说明
- 变体需求

### 5. 补充计算规则

**适用场景**:
- 有复杂的计算规则
- 容易出错的计算逻辑

**贡献方式**:
1. 在 `knowledge/business/calculation_rules/` 创建文档
2. 详细说明计算规则
3. 提供 SQL 示例
4. 说明常见错误

## 贡献流程

### 流程 1: 直接编辑（推荐）

1. 找到要编辑的文档
2. 按照模板格式添加内容
3. 保存
4. 通知团队（如果需要）

### 流程 2: 提交反馈

1. 在 `feedback/knowledge_gaps/` 创建记录
2. 说明缺失的知识
3. 由专人统一补充

### 流程 3: Pull Request

1. Fork 仓库
2. 添加内容
3. 提交 PR
4. Review 后合并

## 文档编写规范

### 格式规范

1. **使用 Markdown 格式**
2. **统一的标题层级**:
   - `#` 一级标题（文档标题）
   - `##` 二级标题（主要章节）
   - `###` 三级标题（子章节）
3. **代码块使用 ```sql```**
4. **表格对齐**

### 内容规范

1. **定义要清晰**:
   - 避免模糊表述
   - 给出具体示例
   - 说明边界情况

2. **示例要完整**:
   - SQL 要有注释
   - 要有示例值
   - 要有说明

3. **保持一致性**:
   - 术语使用一致
   - 格式风格一致
   - 命名规范一致

### 质量标准

- [ ] 定义清晰无歧义
- [ ] 有具体示例
- [ ] 格式符合规范
- [ ] 已经过 Review
- [ ] 已测试验证（如果是 SQL）

## 示例

### 好的贡献示例

```markdown
## 用户粘性

### 定义
用户在一定时期内持续使用产品的程度，通常用 DAU/MAU 比值衡量。

### 计算规则
```
用户粘性 = 月内平均 DAU / MAU
```

### 数据口径
- 分子: 月内每日 DAU 的平均值
- 分母: 月度 MAU

### SQL 示例
```sql
-- 计算 2024 年 1 月的用户粘性
WITH daily_data AS (
    SELECT AVG(dau) as avg_dau
    FROM dws_user_daily
    WHERE date >= '2024-01-01' AND date < '2024-02-01'
),
monthly_data AS (
    SELECT mau
    FROM dws_user_monthly
    WHERE month = '2024-01'
)
SELECT 
    avg_dau,
    mau,
    ROUND(avg_dau / mau, 4) as stickiness
FROM daily_data, monthly_data;
```

### 解读
- 比值越高（接近1），说明用户粘性越强
- 社交产品通常在 0.2-0.5 之间
- 工具产品通常在 0.1-0.3 之间
```

### 不好的贡献示例

```markdown
## 用户粘性

定义: 用户使用产品的程度

计算: DAU/MAU
```

**问题**:
- 定义过于模糊
- 没有具体的计算规则
- 没有 SQL 示例
- 没有使用说明

## 常见问题

### Q: 我不确定某个定义是否准确，可以贡献吗？

A: 可以，但请标注"待确认"，并说明不确定的点。团队会 review 并确认。

### Q: 我发现知识库中的信息有误，怎么办？

A: 
1. 立即在 `feedback/corrections/` 记录
2. 通知负责人
3. 更新文档

### Q: 我应该贡献多详细的内容？

A: 越详细越好，但至少要包含：
- 清晰的定义
- 具体的示例
- 必要的说明

### Q: 我不会写 Markdown，怎么办？

A: 
1. 可以用其他格式（Word/Excel）提供内容
2. 由专人转换为 Markdown
3. 或者学习基础的 Markdown 语法（很简单）
