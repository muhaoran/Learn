# ChatBI 工作流程详解

## 总体流程

```
用户提交需求
    ↓
需求解析 (Parsing)
    ↓
需求澄清 (Clarification) ← 可能需要多轮交互
    ↓
知识检索 (Retrieval)
    ↓
SQL 生成 (Generation)
    ↓
SQL 验证 (Validation)
    ↓
结果输出 (Output)
```

## 详细步骤

### 步骤 1: 需求解析

**目标**: 从自然语言中提取结构化信息

**处理逻辑**:
1. 识别指标关键词（参考 `knowledge/business/metrics/`）
2. 识别维度关键词（参考 `knowledge/business/dimensions/`）
3. 识别时间范围
4. 识别筛选条件
5. 识别聚合方式

**输出**:
```json
{
  "metrics": ["DAU"],
  "dimensions": ["date", "channel"],
  "time_range": {
    "type": "relative",
    "value": "last_7_days"
  },
  "filters": [],
  "aggregation": "daily"
}
```

### 步骤 2: 需求澄清

**目标**: 识别并消除歧义

**检查清单**:
- [ ] 指标定义是否明确？
- [ ] 时间范围是否明确？
- [ ] 维度是否明确？
- [ ] 筛选条件是否完整？
- [ ] 是否有业务黑话需要翻译？

**澄清策略**:
- 优先级排序: 先澄清影响结果最大的问题
- 避免过度提问: 对于有默认规则的，使用默认值
- 提供选项: 给出可能的选项让用户选择

**示例**:
```
您的需求我理解为：查询【最近 7 天】每天的【活跃用户数】，按【注册渠道】分组。

请确认以下几点：
1. "最近 7 天" 是指过去 7 天（含今天）还是过去 7 个完整的自然日（不含今天）？
2. "活跃用户" 是指有任意行为的用户，还是特指某类行为（如登录、发帖等）？
3. "渠道" 是指用户的注册渠道，对吗？
```

### 步骤 3: 知识检索

**目标**: 从知识库中找到相关信息

**检索范围**:
1. **业务知识**: 
   - 指标定义
   - 计算规则
   - 业务术语
   
2. **数据资产**:
   - 相关表
   - 字段信息
   - 关联关系
   
3. **SQL 案例**:
   - 相似需求的 SQL
   - 相关技术方案

**检索策略**:
- 使用关键词匹配
- 使用语义相似度
- 优先使用最新的案例

### 步骤 4: SQL 生成

**目标**: 生成准确的 SQL 语句

**生成原则**:
1. **准确性优先**: 严格按照业务定义生成
2. **性能考虑**: 优先使用汇总表、避免全表扫描
3. **可读性**: 使用 CTE、添加必要注释
4. **健壮性**: 考虑边界情况、空值处理

**生成步骤**:
1. 选择数据表（优先级: ADS > DWS > DWD > ODS）
2. 构建 WHERE 条件
3. 构建 JOIN 关系
4. 构建 SELECT 字段
5. 构建 GROUP BY
6. 构建 ORDER BY
7. 添加注释

### 步骤 5: SQL 验证

**目标**: 确保 SQL 的正确性

**验证维度**:

1. **语法验证**:
   - SQL 语法是否正确
   - 字段名、表名是否存在

2. **逻辑验证**:
   - 是否符合需求
   - 计算逻辑是否正确
   - 去重逻辑是否合理

3. **口径验证**:
   - 是否符合业务定义
   - 计算规则是否一致

4. **性能验证**:
   - 是否有全表扫描
   - 是否缺少必要的索引
   - 是否可以优化

**验证检查点**:
```
✓ 表名和字段名都存在于数据字典中
✓ JOIN 条件使用了正确的关联字段
✓ WHERE 条件包含了分区字段
✓ 指标计算逻辑符合业务定义
✓ 去重维度正确
✓ 时间范围处理正确（时区、边界）
✓ 没有明显的性能问题
```

### 步骤 6: 结果输出

**目标**: 清晰地呈现结果

**输出内容**:
1. **SQL 语句**: 格式化的、带注释的 SQL
2. **执行说明**: 
   - 数据范围
   - 预计数据量
   - 执行建议
3. **结果解释**:
   - 每个字段的含义
   - 计算逻辑说明
4. **注意事项**:
   - 数据时效性
   - 已知限制
   - 使用建议

## 多轮对话处理

### 场景 1: 需求追加

**用户**: "在刚才的基础上，再加上用户等级维度"

**处理**:
1. 解析增量需求
2. 在原 SQL 基础上修改
3. 说明变更点

### 场景 2: 需求调整

**用户**: "不对，我要的是周留存，不是次日留存"

**处理**:
1. 识别变更点
2. 重新生成 SQL
3. 对比说明差异

### 场景 3: SQL 优化

**用户**: "这个 SQL 太慢了，能优化吗？"

**处理**:
1. 分析性能瓶颈
2. 提供优化建议
3. 生成优化后的 SQL

## 异常处理

### 情况 1: 知识库中没有相关信息

**处理**:
1. 明确告知用户缺少哪些信息
2. 请求用户补充
3. 记录到 `feedback/knowledge_gaps/`

### 情况 2: 需求过于模糊

**处理**:
1. 列出所有不确定项
2. 提供常见的理解方式
3. 请求用户确认

### 情况 3: 需求超出能力范围

**处理**:
1. 说明原因
2. 提供替代方案
3. 或建议人工处理

## 质量保证

### 自检清单

生成 SQL 后，AI 应自动检查：

- [ ] SQL 语法正确
- [ ] 所有表名和字段名都在数据字典中
- [ ] 指标计算逻辑符合业务定义
- [ ] 时间范围处理正确
- [ ] 去重逻辑合理
- [ ] JOIN 条件正确
- [ ] WHERE 条件完整
- [ ] 没有明显的性能问题
- [ ] 注释清晰

### 输出格式规范

```markdown
## 需求理解

[复述需求，确认理解正确]

## SQL 语句

```sql
[SQL 代码]
```

## 执行说明

- **数据表**: [使用的表]
- **数据范围**: [时间范围、数据量]
- **预计耗时**: [估计]

## 结果字段说明

| 字段名 | 含义 | 示例值 |
|--------|------|--------|
| ... | ... | ... |

## 注意事项

- [注意事项 1]
- [注意事项 2]
```

## 持续改进

### 反馈收集

每次交互后记录：
- 需求原文
- 生成的 SQL
- 用户反馈（是否准确）
- 修改记录

### 知识库更新

定期（如每周）：
1. 分析反馈数据
2. 识别知识缺口
3. 补充知识库
4. 更新案例库

### 效果评估

定期（如每月）：
1. 统计准确率
2. 分析错误原因
3. 优化 Prompt
4. 优化流程
