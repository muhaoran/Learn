# Skill: 需求澄清

---

## 目标

识别需求中的模糊点和歧义，通过提问澄清，确保准确理解用户需求。

---

## 触发条件

在需求解析后，如果发现不确定项（uncertainties 不为空），触发此技能。

---

## 输入

- 需求解析的结果（包含 uncertainties）
- 用户的原始需求

---

## 处理步骤

### 步骤 1: 评估不确定项的优先级

**优先级规则**:
- **高优先级**: 影响 SQL 核心逻辑的问题
  - 指标不明确
  - 计算规则不明确
  - 时间范围不明确
  
- **中优先级**: 影响结果展示的问题
  - 维度不明确
  - 排序方式不明确
  
- **低优先级**: 可以使用默认值的问题
  - 是否需要限制结果数量
  - 是否需要小数位数

### 步骤 2: 生成澄清问题

**原则**:
- 一次不要问太多问题（最多 3-5 个）
- 提供选项而非开放式问题
- 说明不同选项的差异
- 给出推荐选项（如果有）

**问题模板**:

#### 模板 1: 二选一
```
关于 [问题项]，请确认：
A. [选项 A] - [说明]
B. [选项 B] - [说明]

推荐: [推荐选项]（[推荐理由]）
```

#### 模板 2: 多选一
```
关于 [问题项]，请选择：
1. [选项 1] - [说明]
2. [选项 2] - [说明]
3. [选项 3] - [说明]
```

#### 模板 3: 补充信息
```
请补充以下信息：
- [信息项 1]: [说明为什么需要]
- [信息项 2]: [说明为什么需要]
```

### 步骤 3: 组织澄清消息

**结构**:
```markdown
## 需求理解

[用标准术语复述已理解的部分]

## 需要确认

[列出澄清问题]

## 补充说明

[如果有必要，说明为什么需要澄清这些问题]
```

### 步骤 4: 等待用户回复

用户回复后，更新需求信息，继续下一步。

---

## 输出

澄清问题列表，发送给用户。

---

## 示例（抽象结构）

> 以下示例只给出澄清消息的结构，不绑定具体业务场景。真实澄清时要把 `<xxx>` 替换为实际指标/维度/时间词。

### 结构 1: 单个不确定项（时间范围）

```markdown
## 需求理解

您想查询 <指标名>（<标准定义>）。

## 需要确认

关于时间范围，请确认"<原始表述>"是指：
A. <选项 A 的明确定义 + 实际日期区间>
B. <选项 B 的明确定义 + 实际日期区间>

推荐: <推荐选项>（<推荐理由>）
```

### 结构 2: 指标不明确

```markdown
## 需求理解

您想查询与 <实体> 相关的数据。

## 需要确认

"<原始表述>" 比较宽泛，请问您具体想看：
1. <指标候选 1>（从 `knowledge/metrics/` 匹配得到）
2. <指标候选 2>
3. <指标候选 3>
4. 其他（请说明）

或者您可以直接描述想要分析什么问题，我来帮您确定合适的指标。
```

### 结构 3: 多个不确定项

```markdown
## 需求理解

您想查询 <指标名>，按 <维度> 分组。

## 需要确认

请确认以下几点：

1. **时间范围** - "<原始时间词>" 是指：
   A. <选项 A>
   B. <选项 B>
   C. <选项 C>
   推荐: <推荐选项>（<理由>）

2. **<维度名>** - "<原始维度词>" 是指：
   A. <候选维度 A，说明含义差异>
   B. <候选维度 B，说明含义差异>
   推荐: <推荐选项>（<理由>）
```

## 注意事项

### 1. 避免过度提问

**不好的做法**:
```
请确认：
1. 时间范围？
2. 是否包含今天？
3. 是否需要去重？
4. 是否需要排序？
5. 是否需要限制结果数量？
6. 是否需要保留小数？
7. ...
```

**好的做法**:
```
请确认时间范围：
A. 最近 7 天（含今天）
B. 过去 7 个完整的自然日（不含今天）

其他细节（去重、排序等）我会按照标准规范处理。
```

### 2. 提供上下文

说明为什么需要澄清，帮助用户理解。

**做法**:
- 如果一个词对应多个候选维度/指标，要把各候选的业务意义差异写明，不要只列名称。
- 差异说明应来自 `knowledge/semantics/` 或 `knowledge/metrics/` 里的 `description`，而不是 AI 自行发挥。

### 3. 给出推荐

如果有明显的最佳实践，给出推荐。

**做法**:
- 推荐理由应基于数据口径特性（如数据完整性、分区边界、历史惯例），不要写主观描述。

### 4. 允许用户跳过

对于低优先级的问题，可以使用默认值。

**示例**:
```
如果不需要特别指定，我将使用以下默认设置：
- 结果按日期升序排列
- 保留 2 位小数
- 不限制结果数量
```

## 澄清策略

### 策略 1: 渐进式澄清

对于复杂需求，分多轮澄清：
- 第一轮: 澄清核心问题（指标、时间）
- 第二轮: 澄清细节问题（维度、筛选）

### 策略 2: 假设验证

对于有明显默认理解的需求，先给出假设，让用户确认：

```markdown
我理解您的需求是：[假设的理解]

如果理解有误，请指正。
```

### 策略 3: 提供示例

通过具体日期区间帮助用户理解选项差异（用当前日期 `current_date` 代入计算）：

```markdown
关于时间范围：
A. 最近 7 天（含今天）: <current_date - 6> 到 <current_date>
B. 过去 7 天（不含今天）: <current_date - 7> 到 <current_date - 1>

请选择。
```

## 特殊场景

### 场景 1: 用户使用了错误的术语

**情形**: 用户把两个不同维度的概念拼在一起（例如把一个"指标名"和另一个"与该指标不相容的指标名"合并使用）。

**处理**:
1. 礼貌地指出可能的混淆
2. 询问真实意图
3. 提供正确的表达方式（从 `knowledge/metrics/` 中列出与其意图最接近的指标候选）

### 场景 2: 需求自相矛盾

**情形**: 时间粒度与指标口径不匹配（例如指标本身定义在 A 粒度上，但用户要求在 B 粒度上统计）。

**处理**:
1. 指出矛盾点（指标 `time_window` 或 pattern 隐含的粒度与用户期望粒度冲突）
2. 询问真实意图
3. 提供合理的替代方案（切换到同口径的另一个指标，或调整时间范围）

## 成功标准

- ✅ 所有高优先级不确定项都得到澄清
- ✅ 用户确认理解正确
- ✅ 没有遗漏关键问题
- ✅ 没有过度提问
