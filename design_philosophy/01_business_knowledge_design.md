## 一、设计目标

### 核心问题

**如何让 AI 理解业务？**

传统 Text-to-SQL 的问题：
- ❌ AI 不理解业务术语
- ❌ AI 不知道指标的计算规则
- ❌ AI 臆测业务定义，导致错误
- ❌ 准确率低（60-70%）

我们的目标：
- ✅ 让 AI 掌握业务知识
- ✅ 让 AI 基于知识生成 SQL
- ✅ 保证口径一致性
- ✅ 准确率高（85-95%）

### 设计目标

**建立一套完整的"业务语言系统"**，让 AI 能够：
1. 理解业务术语（包括黑话）
2. 知道从哪些维度分析数据
3. 掌握指标的定义和计算规则
4. 生成准确的 SQL

## 二、核心设计理念

### 理念 1: 语言系统类比

**把业务知识体系类比为一套语言系统**：

```
业务知识层 = 一套完整的"业务语言系统"

├── 术语表 (glossary)      → 词汇表（名词）
│   定义：活跃用户、新增用户、留存用户...
│
├── 维度定义 (dimensions)   → 语法规则（如何描述）
│   定义：日/周/月、新老用户、渠道...
│
├── 指标定义 (metrics)      → 句子（完整表达）
│   定义：DAU、MAU、次日留存率...
│
└── 计算规则 (calculation)  → 语法书（如何组合）
    定义：留存率如何计算、DAU/MAU 如何算...
```

**类比说明**：

| 语言系统 | 业务知识系统 | 作用 |
|---------|-------------|------|
| 词汇表 | 术语表 | 定义基本概念（名词） |
| 语法规则 | 维度定义 | 定义描述角度（形容词、介词） |
| 句子 | 指标定义 | 组合成完整表达 |
| 语法书 | 计算规则 | 定义如何正确组合 |

### 理念 2: 层次递进

**从简单到复杂，从抽象到具体**：

```
第1层：术语表（最简单、最抽象）
   ↓ 被引用
第2层：维度定义（中等复杂）
   ↓ 被组合
第3层：指标定义（较复杂、较具体）
   ↓ 被实现
第4层：计算规则（最复杂、最具体）
```

**设计原因**：
- ✅ 新人学习有路径（从易到难）
- ✅ 修改有范围（改基础层影响广，改上层影响小）
- ✅ AI 理解有顺序（先学基础，再学复杂）

### 理念 3: 解耦和复用

**一次定义，多处使用**：

```
"活跃用户"定义一次
   ↓ 被引用
DAU（日活跃用户）
WAU（周活跃用户）
MAU（月活跃用户）
活跃率
留存率（需要判断活跃）
...
```

**设计原因**：
- ✅ 保证口径一致
- ✅ 减少重复定义
- ✅ 修改一次，全局生效

## 三、四个组成部分详解

### 1️⃣ 术语表 (glossary.md)

#### 定位

**基础词汇层 - 定义业务中的基本概念**

#### 内容结构

```markdown
## [术语名称]

**标准名称**: [标准说法]

**别名/黑话**: 
- [别名1]
- [黑话1]

**定义**: [清晰的定义]

**业务含义**: [业务场景中的含义]

**数据口径**: [统计规则]

**相关术语**: [关联的其他术语]
```

#### 内容示例

```markdown
## 活跃用户

**标准名称**: 活跃用户

**别名/黑话**:
- 活跃
- AU (Active User)
- 有行为的用户

**定义**:
在统计周期内，有任意行为记录的去重用户。

**行为包括**:
- 登录
- 浏览内容
- 发布内容（帖子、评论）
- 点赞、收藏
- 交易行为

**数据口径**:
- 去重维度: user_id
- 统计粒度: 可按日(DAU)、周(WAU)、月(MAU)
- 时间范围: 按行为发生时间统计

**相关术语**:
- DAU、WAU、MAU（活跃用户的不同时间粒度）
- 新增用户（相对概念）
- 流失用户（相对概念）
```

#### 设计要点

- ✅ **最基础的概念** - 不涉及具体计算
- ✅ **包含黑话** - 帮助 AI 理解口语化表达
- ✅ **明确定义** - 避免歧义
- ✅ **建立关联** - 指向相关术语

#### 作用范围

- 被维度定义引用
- 被指标定义引用
- 被计算规则引用
- 被 AI 用于需求解析

**使用场景**: [什么时候用]

**SQL 示例**: [如何在 SQL 中使用]
```

#### 内容示例

```markdown
## 时间维度 - 日

**定义**: 自然日，00:00:00 - 23:59:59

**字段格式**: YYYY-MM-DD (如 2024-01-01)

**SQL 实现**: 
- 提取日期: cast(timestamp_column as date)
- 当前日期: current_date
- 日期运算: date_add('day', n, date)

**使用场景**:
- 查询某一天的数据
- 按天聚合趋势
- 计算同比/环比

## 用户维度 - 新老用户

**定义**: 按注册时间划分用户

**分类规则**:
- 新用户: 注册时间 <= 30天
- 老用户: 注册时间 > 30天

**数据字段**: register_date

**SQL 实现**:
```sql
case 
    when date_diff('day', register_date, current_date) <= 30 
    then '新用户'
    else '老用户'
end as user_type
```

**使用场景**:
- 新老用户行为对比
- 分渠道新老用户分析
```

- ✅ **定义观察角度** - 数据分析的"切面"
- ✅ **引用术语** - 使用术语表中的概念
- ✅ **可组合** - 多个维度可以组合使用
- ✅ **提供实现** - 包含 SQL 实现方法

#### 作用范围

- 被指标定义引用（指标在哪些维度上统计）
- 被 SQL 生成使用（GROUP BY、WHERE 条件）
- 帮助 AI 理解分组和筛选需求

```
DAU = COUNT(DISTINCT user_id)

- [活跃用户](../glossary.md#活跃用户)

- [日](../dimensions/time_dimensions.md#日)

**数据来源**:
- **推荐表**: dws_user_daily.dau (汇总表，性能好)
- **明细表**: dwd_user_behavior (可自定义行为类型)

**使用场景**:
- 日常运营监控
- 趋势分析
- 同比/环比分析

**注意事项**:
- 节假日会有波动
- 需要考虑异常值（如刷量）
- 与 MAU 配合使用可计算粘性

**SQL 示例**:
参考: knowledge/sql_examples/user_analysis/dau_trend.md
```

### 4️⃣ 计算规则 (calculation_rules/)

#### 定位

**实现方法层 - 定义复杂指标的详细计算方法**

#### 内容结构

```markdown
## [规则名称]

**适用指标**: [哪些指标使用这个规则]

**涉及的术语**: [引用的术语]

**涉及的维度**: [引用的维度]

**计算公式**: [数学公式]

**计算步骤**: [详细步骤]

**SQL 模板**: [完整的 SQL 模板]

**注意事项**: [常见错误]

**变体场景**: [不同场景的处理]
```

#### 内容示例

```markdown
## 次日留存率计算规则

**适用指标**: 
- 次日留存率
- D1 留存率
- 新用户次日留存

**涉及的术语**:
- [新增用户](../glossary.md#新增用户) - 基准用户
- [活跃用户](../glossary.md#活跃用户) - 判断是否留存
- [留存用户](../glossary.md#留存用户) - 计算目标

**涉及的维度**:
- [日](../dimensions/time_dimensions.md#日) - 时间粒度
- D0: 注册日
- D1: 注册日 + 1天

**计算公式**:
```
次日留存率 = D1活跃用户数 / D0新增用户数 × 100%
```

**计算步骤**:

步骤 1: 确定基准用户（D0）
- 找到指定日期注册的用户
- 记录每个用户的注册日期

步骤 2: 找到留存用户（D1）
- 对于每个基准用户
- 查找其在 D1（注册日+1天）的活跃记录
- 有活跃记录 = 留存

步骤 3: 计算留存率
- 分子: 留存用户数
- 分母: 基准用户数
- 计算比例

**SQL 模板** (Trino 语法):
```sql
WITH base_users AS (
    -- 步骤1: D0 基准用户
    SELECT 
        user_id,
        cast(register_time as date) as register_date
    FROM 
        dwd_user_register
    WHERE 
        register_date = date '2024-01-01'  -- D0
),
retention_users AS (
    -- 步骤2: D1 留存用户
    SELECT 
        bu.user_id,
        bu.register_date
    FROM 
        base_users bu
    INNER JOIN 
        dwd_user_behavior ub
    ON 
        bu.user_id = ub.user_id
        -- 关键: D1 = D0 + 1天
        AND ub.date = date_add('day', 1, bu.register_date)
)
-- 步骤3: 计算留存率
SELECT 
    COUNT(DISTINCT bu.user_id) as base_users_count,     -- 分母
    COUNT(DISTINCT ru.user_id) as retention_users_count, -- 分子
    ROUND(
        CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
        / COUNT(DISTINCT bu.user_id), 
        2
    ) as retention_rate                                  -- 留存率
FROM 
    base_users bu
LEFT JOIN  -- 必须用 LEFT JOIN，保留未留存用户
    retention_users ru
ON 
    bu.user_id = ru.user_id;
```

**关键技术点**:

1. **必须使用 LEFT JOIN**
   - ❌ 错误: INNER JOIN 会遗漏未留存用户
   - ✅ 正确: LEFT JOIN 保留所有基准用户

2. **时间计算要精确**
   - D1 = date_add('day', 1, register_date)
   - 不能用 >= 和 <=，要精确到天

3. **去重要正确**
   - 分子、分母都要 DISTINCT
   - 按 user_id 去重

4. **除法要注意类型**
   - 转换为 DOUBLE 避免整数除法
   - 处理分母为 0 的情况

**常见错误**:

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 使用 INNER JOIN | 遗漏未留存用户，分母变小，留存率虚高 | 使用 LEFT JOIN |
| 时间计算错误 | 统计的不是 D1，而是其他天 | 精确使用 date_add('day', 1, d0) |
| 没有去重 | 重复计数，数值错误 | COUNT(DISTINCT user_id) |
| 整数除法 | 丢失小数精度 | CAST AS DOUBLE |

**变体场景**:

1. **按渠道分组的次日留存**
   - 在 base_users 中添加 register_channel
   - 在最终 SELECT 中添加 GROUP BY register_channel

2. **7日留存、30日留存**
   - 修改时间计算: date_add('day', 7, register_date)
   - 其他逻辑相同

3. **留存曲线（D1, D3, D7, D15, D30）**
   - 使用 UNION ALL 组合多个留存天数
   - 或使用窗口函数
```

#### 设计要点

- ✅ **最详细的说明** - 每个步骤都解释清楚
- ✅ **提供 SQL 模板** - 可以直接参考
- ✅ **标注常见错误** - 避免踩坑
- ✅ **提供变体** - 适应不同场景

#### 作用范围

- 被 AI 用于生成复杂 SQL
- 指导 AI 选择正确的 JOIN 类型
- 提供时间计算的方法
- 避免常见的计算错误

## 五、完整的工作流程示例

### 用户需求

> "查询 1 月份新用户的次日留存率，按渠道分组"

### AI 的知识检索和使用过程

#### 阶段 1: 需求解析（使用术语表）

```
输入: "1月份新用户的次日留存率，按渠道分组"

AI 查询 glossary.md:
  - "新用户" → 找到定义: 在统计周期内完成注册的用户
  - 确认: 统计对象是 user_id，按注册时间
  
提取结果:
  - 指标: 次日留存率
  - 对象: 新用户（新增用户）
  - 时间范围: 1月份
  - 分组维度: 渠道
```

#### 阶段 2: 维度识别（使用维度定义）

```
AI 查询 dimensions/time_dimensions.md:
  - "1月份" → 找到定义: 自然月 2024-01-01 到 2024-01-31
  - SQL: date >= date '2024-01-01' AND date < date '2024-02-01'
  
AI 查询 dimensions/user_dimensions.md:
  - "渠道" → 找到定义: register_channel 字段
  - SQL: GROUP BY register_channel
  
提取结果:
  - 时间范围: 2024-01-01 到 2024-01-31
  - 分组字段: register_channel
```

#### 阶段 3: 指标理解（使用指标定义）

```
AI 查询 metrics/user_metrics.md:
  - "次日留存率" → 找到定义
  - 计算公式: D1活跃用户数 / D0新增用户数 × 100%
  - 数据来源: dwd_user_register + dwd_user_behavior
  
提取结果:
  - 需要两张表: 注册表、行为表
  - 计算逻辑: 比例计算
  - 需要关联: user_id
```

#### 阶段 4: 获取计算规则（使用计算规则）

```
AI 查询 calculation_rules/retention.md:
  - "次日留存率" → 找到详细计算规则
  - 获取 SQL 模板
  - 了解关键技术点:
    - 必须用 LEFT JOIN
    - D1 = date_add('day', 1, D0)
    - 两边都要 DISTINCT
  - 了解常见错误:
    - 不能用 INNER JOIN
    - 时间计算要精确
  
提取结果:
  - SQL 结构: WITH ... LEFT JOIN ...
  - 时间计算: date_add('day', 1, register_date)
  - JOIN 类型: LEFT JOIN
```

#### 阶段 5: 组合生成 SQL

```
基于知识库生成:

1. 从 retention.md 获取 SQL 模板
2. 填入时间范围（从 time_dimensions）
3. 添加渠道分组（从 user_dimensions）
4. 使用 Trino 语法（从 trino_syntax_guide）
5. 添加注释说明（来自各知识点）

生成完整的 SQL（见前面的示例）
```

## 六、设计的内在逻辑

### 逻辑 1: 分层解耦

**为什么分成四个部分，而不是一个大文件？**

**答案**: 解耦，便于维护

```
场景: "活跃用户"的定义变了

如果是一个大文件:
  - 需要找到所有提到"活跃用户"的地方
  - 逐个修改
  - 容易遗漏
  - 容易不一致

如果是分层设计:
  - 只修改 glossary.md 中"活跃用户"的定义
  - 所有引用它的地方自动获得新定义
  - 保证一致性
```

### 逻辑 2: 组合而非重复

**为什么不在每个指标中重复定义术语？**

**答案**: 复用，避免重复

```
如果重复定义:
  DAU 定义中: "活跃用户是..."
  WAU 定义中: "活跃用户是..."
  MAU 定义中: "活跃用户是..."
  
  问题: 定义不一致的风险

如果引用定义:
  所有指标都引用 glossary.md 中的"活跃用户"
  
  好处: 一处定义，多处复用
```

### 逻辑 3: 从简单到复杂

**为什么是这个顺序？**

**答案**: 学习路径

```
新人学习业务:
1. 先看术语表 → 理解基本概念（简单）
   "什么是活跃用户？"
   
2. 再看维度定义 → 理解分析角度（中等）
   "可以按日、按周、按渠道来看"
   
3. 然后看指标定义 → 理解业务度量（较复杂）
   "DAU = 日 + 活跃用户数"
   
4. 最后看计算规则 → 理解复杂计算（最复杂）
   "次日留存率的完整计算步骤"
```

### 逻辑 4: 单一职责

**每个部分只负责一件事**：

| 部分 | 职责 | 不负责 |
|------|------|--------|
| 术语表 | 定义概念 | ❌ 不涉及计算 |
| 维度定义 | 定义角度 | ❌ 不涉及具体指标 |
| 指标定义 | 定义度量 | ❌ 不写详细步骤 |
| 计算规则 | 详细实现 | ❌ 不重复基础定义 |

**好处**：
- 职责清晰
- 便于维护
- 减少冗余

## 七、实际案例：完整追溯

### 案例：生成"1月新用户的次日留存率"的 SQL

#### 知识流转图

```
用户需求: "1月份新用户的次日留存率，按渠道分"
    ↓
┌─────────────────────────────────────────────┐
│ 步骤1: 术语识别 (glossary.md)               │
├─────────────────────────────────────────────┤
│ "新用户" → 注册用户                          │
│ "留存" → 在后续时间点仍活跃                  │
│ 提取: 基准用户、活跃定义                     │
└─────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────┐
│ 步骤2: 维度解析 (dimensions/)                │
├─────────────────────────────────────────────┤
│ "1月份" → time_dimensions.md                │
│   SQL: date >= '2024-01-01' AND < '2024-02-01' │
│ "按渠道" → user_dimensions.md               │
│   SQL: GROUP BY register_channel            │
└─────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────┐
│ 步骤3: 指标理解 (metrics/user_metrics.md)   │
├─────────────────────────────────────────────┤
│ "次日留存率" → 找到指标定义                  │
│ 公式: D1活跃数 / D0新增数 × 100%            │
│ 数据表: dwd_user_register + dwd_user_behavior │
└─────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────┐
│ 步骤4: 计算规则 (calculation_rules/retention.md) │
├─────────────────────────────────────────────┤
│ "次日留存率" → 找到详细计算规则              │
│ SQL模板: WITH base_users AS ... LEFT JOIN ... │
│ 关键点: LEFT JOIN、时间计算、去重           │
└─────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────┐
│ 步骤5: 组合生成 SQL                          │
├─────────────────────────────────────────────┤
│ 1. 使用 retention.md 的 SQL 模板             │
│ 2. 填入时间范围（2024-01-01 到 2024-01-31） │
│ 3. 添加渠道分组（GROUP BY register_channel）│
│ 4. 使用 Trino 语法                          │
└─────────────────────────────────────────────┘
    ↓
生成的 SQL（完整、准确、符合 Trino 语法）
```

#### 知识引用追溯

生成的 SQL 的每个部分都可以追溯到知识来源：

```sql
WITH new_users AS (
    -- 来源: glossary.md "新增用户"定义
    -- 来源: time_dimensions.md "1月份"定义
    SELECT 
        user_id,
        cast(register_time as date) as register_date,
        register_channel  -- 来源: user_dimensions.md
    FROM 
        dwd_user_register  -- 来源: user_metrics.md 指定的数据源
    WHERE 
        -- 来源: time_dimensions.md 的时间范围实现
        register_date >= date '2024-01-01'
        AND register_date < date '2024-02-01'
),
retention_users AS (
    -- 来源: glossary.md "留存用户"定义
    SELECT 
        nu.user_id,
        nu.register_date,
        nu.register_channel
    FROM 
        new_users nu
    INNER JOIN 
        dwd_user_behavior ub  -- 来源: user_metrics.md 指定的数据源
    ON 
        nu.user_id = ub.user_id
        -- 来源: retention.md 的时间计算规则
        -- 来源: trino_syntax_guide.md 的 date_add 函数
        AND ub.date = date_add('day', 1, nu.register_date)
)
SELECT 
    nu.register_channel,  -- 来源: user_dimensions.md
    COUNT(DISTINCT nu.user_id) as new_users_count,
    COUNT(DISTINCT ru.user_id) as retention_users_count,
    -- 来源: user_metrics.md 的计算公式
    -- 来源: retention.md 的精度处理要求
    ROUND(
        CAST(COUNT(DISTINCT ru.user_id) AS DOUBLE) * 100.0 
        / COUNT(DISTINCT nu.user_id), 
        2
    ) as retention_rate
FROM 
    new_users nu
LEFT JOIN  -- 来源: retention.md 的 JOIN 类型要求（关键！）
    retention_users ru
ON 
    nu.user_id = ru.user_id
    AND nu.register_date = ru.register_date
    AND nu.register_channel = ru.register_channel
GROUP BY 
    nu.register_channel  -- 来源: user_dimensions.md
ORDER BY 
    nu.register_channel;
```

### ✅ 优势

#### 1. **口径一致性**

```

  → 都用同一个计算规则

```

#### 2. **可追溯性**

```
为什么用 LEFT JOIN？
  → 追溯到 retention.md
  → 找到解释: 避免遗漏未留存用户
  
为什么时间是 date_add('day', 1, xxx)?
  → 追溯到 retention.md
  → 找到解释: D1 = D0 + 1天
```

```
"活跃用户"定义变化:
  - 只改 glossary.md
  - 所有引用自动更新
  - DAU、WAU、MAU、留存率都自动调整

```

## 十、设计的哲学思考

### 问题 1: 为什么要分四个部分？

**不能合并为一个或两个吗？**

**答案**: 可以合并，但分开更好

**合并的问题**：
```
如果合并为一个"业务知识.md":
  - 文件太大，难以维护
  - 修改一个概念影响不清晰
  - AI 难以精确检索
  - 人类难以快速查找
```

**分开的好处**：
```
分成四个部分:
  - 每个文件聚焦一个方面
  - 职责单一，便于维护
  - AI 精确检索（只看需要的部分）
  - 人类快速定位（知道去哪里找）
```

### 问题 2: 为什么需要计算规则，不能直接写在指标定义中？

**答案**: 分离定义和实现

**不分离的问题**：
```
在 user_metrics.md 中写所有细节:
  - 文件太长（每个指标都很详细）
  - 简单指标和复杂指标混在一起
  - 难以查找
```

**分离的好处**：
```
指标定义: 简洁，只写"是什么"
计算规则: 详细，写"怎么做"

好处:
  - 简单指标不需要看计算规则
  - 复杂指标有详细的实现指导
  - 职责清晰
```

### 问题 3: 为什么维度要单独定义？

**答案**: 维度是跨指标复用的

**示例**：
```
"日"这个维度被多个指标使用:
  - DAU（日活跃用户数）
  - 日新增用户数
  - 日发帖数
  - 日交易额
  ...

如果不单独定义:
  - 每个指标都要重复定义"日"
  - 可能定义不一致
  - 修改"日"的定义需要改多处
```

## 十一、最佳实践建议

### 添加新术语时

```markdown
✅ 必须做:
1. 在 glossary.md 中添加清晰的定义
2. 说明包含哪些情况、不包含哪些情况
3. 列出所有已知的别名和黑话
4. 标注相关术语

❌ 不要做:
- 定义模糊不清
- 没有列出黑话
- 与其他术语冲突
```

### 添加新指标时

```markdown
✅ 必须做:
1. 在对应的 metrics/ 文件中添加
2. 明确引用的术语和维度
3. 提供计算公式
4. 指明数据来源
5. 如果复杂，创建对应的计算规则文档

❌ 不要做:
- 重复定义已有的术语
- 不标注引用关系
- 计算规则模糊
```

### 添加新维度时

```markdown
✅ 必须做:
1. 在对应的 dimensions/ 文件中添加
2. 说明分类规则
3. 提供 SQL 实现
4. 说明使用场景

❌ 不要做:
- 与已有维度冲突
- 没有 SQL 实现示例
```

### 添加新计算规则时

```markdown
✅ 必须做:
1. 说明适用的指标
2. 列出引用的术语和维度
3. 提供完整的 SQL 模板
4. 标注常见错误
5. 提供变体场景

❌ 不要做:
- 重复基础定义
- SQL 模板不完整
- 没有说明常见错误
```

## 十二、总结

### 核心设计逻辑

```
术语表 = 基础词汇（名词）
   ↓ 定义概念
维度定义 = 描述角度（形容词）
   ↓ 提供观察切面
指标定义 = 业务度量（句子）
   ↓ 组合成完整表达
计算规则 = 实现方法（语法书）
   ↓ 详细实现步骤
```

### 协同方式

```
1. 术语表定义基础概念
2. 维度定义观察角度
3. 指标定义引用术语和维度，形成完整度量
4. 计算规则引用所有，提供详细实现
```

### 价值

- ✅ **解耦**: 修改一处，影响清晰
- ✅ **复用**: 一次定义，多处使用
- ✅ **一致**: 统一口径，结果一致
- ✅ **可追溯**: 每个决策有依据
- ✅ **可维护**: 职责清晰，便于更新
- ✅ **可扩展**: 新增内容有章可循
