四层可组合知识架构

核心设计理念：维护少量语义原子和计算模式，通过组合覆盖无限的指标空间。每层职责单一、互相解耦，信息不跨层重复。

~10 个计算模式 × ~100 个语义原子 = 覆盖 90%+ 业务指标
组合而非枚举 — 知识库的价值在于「组合能力」，不在于「预存答案数量」
Layer D 指标目录 Metrics

「是哪个组合有名字」 — 极薄的声明式配置，只写「用哪个模式 + 填哪些原子」，不写定义不写 SQL。仅登记口径需固化的高频指标，大多数查询由 AI 即时组合。

dau.yaml mau.yaml new_user_count.yaml d1_retention_rate.yaml d7_retention_rate.yaml post_user_count.yaml trichotomy_aum.yaml fund_first_purchase_users.yaml
Layer C 计算模式 Patterns

「怎么算」 — 可复用的参数化 SQL 模板，定义通用的计算结构。业务无关，只关心计算方式。参数类型引用语义层，形成层间接口契约。

count_distinct 去重计数 cohort_retention 队列留存 sum_metric 求和指标 比值类（分子分母组合） 漏斗转化 funnel 同比环比 period_over_period
Layer B 业务语义 Semantics

「是什么意思」 — 把业务语言翻译成数据条件，是系统的单一权威来源。三类语义原子以实体为锚点组织，真正需要投入精力维护的核心层。

实体 Entities
user 用户fund_product 基金
业务过程 Events
注册活跃行为发帖评论基金购买基金首购
维度 Dimensions
注册渠道平台行为类型计算标签持仓量基金类型
Layer A 数据字典 Schema

「有什么」 — 描述数据仓库的物理事实：表名、字段名、类型、分区键、更新频率。纯客观事实，不含业务判断，理论上可从 Metastore 自动生成。

dws_user_daily dwd_user_behavior dwd_user_register dwd_ast_pub_daily_holding_detail dws_evt_parent_money_first_trade +20 tables

六步标准工作流程

每个数据需求都按照标准化流程处理，步骤间有明确的数据流转，确保输出质量一致、可追溯

🔍
① 需求解析 Skill #1
从自然语言中提取结构化信息：指标名称、维度（group_by）、时间范围、筛选条件。读取 metrics/ 和 semantics/ 的 aliases 字段匹配业务黑话，翻译为标准术语。标记不确定项。
输入：自然语言需求 输出：结构化需求 {metrics, dimensions, time_range, filters, uncertainties}
❓
② 需求澄清 Skill #2 · 仅当有 uncertainties 时触发
按优先级处理不确定项：高（影响 SQL 核心逻辑） > 中（影响结果展示） > 低（可用默认值）。以选项方式提问（而非开放式），给出推荐选项和差异说明。一次最多 3-5 个问题，避免过度提问。支持渐进式澄清、假设验证、示例辅助三种策略。
输入：uncertainties 列表 输出：澄清后的确定性需求 可能循环：用户回复后更新需求
📖
③ 知识检索 Skill #3
按四层依次展开：metrics/ 找到指标配方 → patterns/ 获取 SQL 模板和参数定义 → semantics/ 将 Entity/Event/Dimension/NamedValue 展开为表名、字段名、SQL 条件 → schema/ 确认字段存在、获取分区信息。知识缺失时主动告知用户。
输入：确定性需求 输出：retrieval_result {pattern, semantic_resolution, schema_validation}
⚙️
④ SQL 生成 Skill #4
展开 Pattern 模板，代入语义参数：Entity → primary_key、Event → source_table + type_condition、Dimension → sql_expr（SELECT/GROUP BY）、NamedValue → sql_condition（WHERE 子查询）。优先使用汇总表（ADS > DWS > DWD > ODS），必须包含分区条件，使用 CTE 提高可读性，使用 NULLIF 防除零。
输入：retrieval_result 输出：Trino SQL 语句
✅
⑤ SQL 验证 Skill #5
六维自检：语法（关键字/括号/逗号）→ 字段存在性（对照 schema/ 逐一验证）→ 逻辑（去重/JOIN类型/时间计算）→ 口径一致性（对照 metrics/ 定义）→ 性能（分区条件/表选择/时间范围）。发现问题时自动修复后重新验证。
输入：SQL + 需求 + 业务定义 输出：验证通过的 SQL 不通过则回退修复
📊
⑥ 结果输出 Skill #6
标准化输出六个部分：需求复述（确认理解）→ 格式化 SQL（带注释）→ 技术方案（使用的表/计算逻辑/关键技术点）→ 执行说明（数据范围/预计耗时）→ 结果字段说明（含义/示例值/单位）→ 注意事项（性能/数据质量风险）。
输入：验证通过的 SQL + 需求信息 输出：完整的 SQL + 说明文档

AI 技能模块

7 个标准化技能文档定义了 AI 在每个环节的行为规范、触发条件和输入输出。Skill #1-#6 对应查询主流程，Skill #7 负责知识库自动扩充。

01
需求解析
触发：用户提交数据需求时

从自然语言提取指标、维度、时间范围、筛选条件，匹配 aliases 翻译业务黑话，标记不确定项

输入：自然语言 输出：结构化需求 JSON
02
需求澄清
触发：存在 uncertainties 时

按优先级（高/中/低）提问，选项式而非开放式，给出推荐选项和差异说明，最多 3-5 个问题

输入：不确定项列表 输出：确定性需求
03
知识检索
触发：需求澄清完成后

按四层依次展开 metrics → patterns → semantics → schema，将语义 ID 解析为表名、字段名和 SQL 条件

输入：确定性需求 输出：retrieval_result
04
SQL 生成
触发：知识检索完成后

展开 Pattern 模板，代入语义参数（Entity/Event/Dimension/NamedValue），优先汇总表，必须带分区条件

输入：retrieval_result 输出：Trino SQL
05
SQL 验证
触发：SQL 生成后、输出前

五维自检：语法正确性 → 字段存在性 → 逻辑合理性 → 口径一致性 → 性能风险。不通过则自动修复后重新验证

输入：SQL + 业务定义 输出：验证通过的 SQL
06
结果输出
触发：SQL 验证通过后

标准化输出：需求复述 → 格式化 SQL → 技术方案 → 执行说明 → 结果字段含义 → 注意事项

输入：验证通过的 SQL 输出：完整文档
07
原始知识处理 独立于查询主流程，负责知识库的自动扩充
触发：用户将原始资料放到 raw_knowledge/mixed/ 并请求处理

接受任意格式（Excel / Word / SQL / PDF / Markdown / 会议记录等），AI 自动识别内容类型、提取关键信息、智能补全、按新架构四层分类写入知识库，最后归档原始文件。完全不依赖用户标注，混杂内容也能处理。处理后输出详细报告，不确定的地方主动提问。

输入：raw_knowledge/mixed/ 中的任意文件 输出：知识库更新 + 处理报告 + 原始文件归档 详见下方「知识库扩充流程」

端到端示例

以「查询昨天的 DAU」为例，展示从自然语言到 SQL 的完整推导路径

💬 用户："查询昨天的 DAU"
Step 1 · 需求解析
识别指标: DAU（日活跃用户数），时间: 昨天，无分组维度
Step 2 · 指标目录
匹配 metrics/dau.yaml → pattern: count_distinct，entity: user，event: active_behavior
Step 3 · 计算模式
展开 patterns/count_distinct.yaml → COUNT(DISTINCT ${entity.primary_key}) FROM ${event.source_table}
Step 4 · 业务语义
Entity(user) → primary_key: user_id；Event(active_behavior) → source_table: dwd_user_behavior；可优化：改用汇总表 dws_user_daily
Step 5 · 数据字典
确认 dws_user_daily 分区字段: date，字段 user_id / is_active 存在 ✅
Step 6 · 生成 SQL
-- DAU：昨天的日活跃用户数（使用汇总表） SELECT date, COUNT(DISTINCT user_id) AS dau FROM dws_user_daily WHERE date = date_add('day', -1, current_date) AND is_active = 1 GROUP BY date
💬 用户："1 月份新用户的次日留存率，按渠道分"
Step 1 · 需求解析
指标: 次日留存率，时间: 1 月份，筛选: 新用户，维度: 渠道
Step 2 · 指标目录
匹配 metrics/d1_retention_rate.yaml → pattern: cohort_retention，base: registration，retain: active_behavior，offset_days: 1
Step 3 · 计算模式
展开 patterns/cohort_retention.yaml → CTE 结构：base 队列 → retained 留存 → LEFT JOIN 计算比率
Step 4 · 业务语义
Event(registration) → dwd_user_register； Event(active_behavior) → dwd_user_behavior； Dimension(register_channel) → register_channel from dwd_user_register
Step 5 · 生成 SQL
-- 1 月新用户次日留存率，按注册渠道分组 WITH cohort AS ( SELECT user_id, register_date, register_channel FROM dwd_user_register WHERE register_date >= DATE '2024-01-01' AND register_date < DATE '2024-02-01' ), retained AS ( SELECT DISTINCT b.user_id FROM dwd_user_behavior b JOIN cohort c ON b.user_id = c.user_id WHERE b.date = date_add('day', 1, c.register_date) ) SELECT c.register_channel, COUNT(DISTINCT c.user_id) AS cohort_size, COUNT(DISTINCT r.user_id) AS retained_count, ROUND(COUNT(DISTINCT r.user_id) * 100.0 / NULLIF(COUNT(DISTINCT c.user_id), 0), 2) AS retention_rate FROM cohort c LEFT JOIN retained r ON c.user_id = r.user_id GROUP BY c.register_channel ORDER BY c.register_channel

AI 行为规范

通过 .cursorrules 定义 AI 的角色边界、行为准则和安全规范

🎯 核心原则

  • ✓ 准确性第一 — SQL 必须完全符合业务口径
  • ✓ 主动澄清 — 遇到模糊需求必须提问
  • ✓ 知识驱动 — 严格基于知识库生成 SQL
  • ✓ 可解释性 — 清晰说明 SQL 逻辑
  • ✓ Trino 语法 — 所有 SQL 必须符合 Trino

📝 SQL 生成规范

  • ✓ 优先使用汇总表（ADS > DWS > DWD > ODS）
  • ✓ 必须包含分区字段条件
  • ✓ 使用 CTE 提高复杂 SQL 可读性
  • ✓ 除法必须用 NULLIF 防除零

设计原则

五条核心设计原则，确保系统可维护、可扩展、可穷尽

单一事实来源

每个业务语义只在一个地方定义（Semantics），不在多层重复描述。修改活跃行为定义？只改 semantics/events/active_behavior.yaml 一处。

组合而非枚举

知识库的价值在于「组合能力」。1000 个指标不是 1000 份文档，而是少量语义原子和计算模式的组合空间。

越高层越薄

指标目录（Metric）是最薄的一层，每条只有 4-8 行配置。它不承载定义职责，只是一个「配方」。

可穷尽的边界

真正需要维护的语义原子（~100 个）和计算模式（~10 个）是有限的，可以穷尽、可以维护。

改一处，影响全局

口径变更只动 Semantics，模式调整只动 Pattern。修改「活跃行为」范围？所有依赖它的指标自动更新。
